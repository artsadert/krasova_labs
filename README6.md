# Лабораторная работа №6. Что происходит с backend-сервисом после шардирования

Анализ реальных запросов сервиса **Triply-User** после распределения данных
между четырьмя независимыми PostgreSQL: какие запросы остались
одношардовыми, какие стали распределёнными и что ломается при отказе шарда.

Все выводы подкреплены замерами на живом стенде. Полный протокол — схема, код
и вывод — в [`result6.md`](result6.md), сырой вывод — в
`lab6/results/lab6_raw.txt`.

## Сервис

**Triply-User** — микросервис профилей платформы такси Triply
(`~/programs/TaxiApp/Triply-User`): профили пассажиров и водителей, машины,
оценки после поездок, статус доступности водителя.

- Go, clean/hexagonal архитектура, GORM
- gRPC `:50052`, REST (Gin) `:8082`
- PostgreSQL: `users`, `riders`, `drivers`, `vehicles`, `ratings` + Redis (кеш
  доступности водителей, TTL 60 с)

Все SQL-запросы в отчёте взяты из реального кода
`internal/infrastructure/postgresrepo/{driver,rider,rating}.go`, а имена
эндпойнтов — из `internal/interface/rest/router.go`.

## Стенд: сервис действительно запущен

Лабораторная выполнена не на макете, а на работающем сервисе. Поднято
**четыре экземпляра Triply-User**, каждый со своим шардом, и router
направляет HTTP-запросы по shard key.

| Шард | Экземпляр сервиса | PostgreSQL | drivers | available |
|---|---|---|---:|---:|
| shard0 | `http://127.0.0.1:8090` | `:5440` | 2 807 | 896 |
| shard1 | `http://127.0.0.1:8091` | `:5441` | 2 204 | 740 |
| shard2 | `http://127.0.0.1:8092` | `:5442` | 2 544 | 838 |
| shard3 | `http://127.0.0.1:8093` | `:5443` | 2 445 | 832 |

| Параметр | Значение |
|---|---|
| Сервис | Triply-User, собран из исходников (Go 1.27), `AUTO_MIGRATE=true` |
| Шарды | 4 независимых PostgreSQL 18.6, порты 5440-5443 |
| Shard key | `user_id` |
| Маршрутизация | consistent hash ring (из лабораторной №5), 150 vnodes |
| Данные | 50 000 профилей, 10 000 водителей с машинами, 200 000 оценок |

Две вещи пришлось решить, чтобы сервис поднялся без Docker (демон остановлен)
и без Redis (не установлен):

- **PostgreSQL** запущен нативно через `initdb`/`pg_ctl` — четыре кластера
  плюс отдельный для первых проверок сервиса;
- **Redis** заменён минимальным сервером протокола RESP на Python
  (`lab6/service/redis_stub.py`, ~120 строк). Сервису он нужен только под кеш
  доступности водителя: `PING`, `SET` с TTL, `GET`. Этого хватило, чтобы
  `PUT/GET /v1/drivers/{id}/availability` работали штатно.

Все сценарии ниже выполняются Python-скриптами по HTTP к настоящему REST API
(`lab6/app/run_lab6_service.py`); прямой SQL используется только там, где через
API не видно внутренностей.

Шардируются по `user_id` **все** таблицы: `users.id`, `riders.user_id`,
`drivers.user_id`, `vehicles.driver_id`, `ratings.ratee_id`.

```text
шард           users   drivers  vehicles   ratings
shard0        13,966     2,807     2,807    56,774
shard1        11,126     2,204     2,204    43,187
shard2        12,650     2,544     2,544    51,352
shard3        12,258     2,445     2,445    48,687
итого         50,000    10,000    10,000   200,000
```

# 1. Архитектура после шардирования

```
          REST /v1 · gRPC user.v1.UserService
                        │
                    Router  (hash ring, shard key = user_id)
        ┌───────────┬────┴──────┬───────────┐
        ▼           ▼           ▼           ▼
     shard0      shard1      shard2      shard3
     :5440       :5441       :5442       :5443
```

Router — единственное место, которое знает, где лежит запись. Шарды друг о
друге не знают: у них нет общего WAL (в отличие от Primary/Replica из
лабораторной №4) и нет общего каталога.

Важное наблюдение о самом сервисе: `DriverRepository.GetByID` и
`DriverRepository.List` **уже** не используют SQL JOIN — они делают несколько
отдельных запросов и собирают объект в Go (`map[string]UserModel`,
`map[string]VehicleModel`). Комментарий в коде — «Two batched reads instead of
2N per-row lookups». Это ровно тот приём, к которому шардирование принуждает,
так что часть сервиса оказалась готова к нему заранее.

# 2. Single-Shard Query

**Запрос:** `GET /v1/drivers/{user_id}` → `DriverRepository.GetByID`

```go
r.db.First(&dm, "user_id = ?", userID)      // drivers
r.db.First(&u,  "id = ?", userID)           // users
r.db.First(&vm, "driver_id = ?", userID)    // vehicles
```

Реальные вызовы REST API через router:

```text
   b4dc35bc...  router -> shard0     38.1 мс   Driver 1618, машина A1618BC
   73b2ea7a...  router -> shard1     30.8 мс   Driver 3611, машина A3611BC
   bcf09afa...  router -> shard2     19.1 мс   Driver 4503, машина A4503BC
   20570d50...  router -> shard3     19.6 мс   Driver 6407, машина A6407BC
```

**Чем это доказано.** На шарде включён `log_statement = 'all'`, после чего
сделан один вызов `GET /v1/drivers/{user_id}`. Вот что сервис отправил в
PostgreSQL на самом деле:

```sql
SELECT * FROM "drivers"  WHERE user_id  = $1 ORDER BY "drivers"."user_id" LIMIT $2
SELECT * FROM "users"    WHERE id       = $1 ORDER BY "users"."id"        LIMIT $2
SELECT * FROM "vehicles" WHERE driver_id = $1 ORDER BY "vehicles"."id"    LIMIT $2
```

Ровно три запроса, все — к одному шарду и все по одному и тому же значению
ключа. Видно и то, что GORM использует подготовленные выражения (в логе они
идут как `execute stmtcache_<hash>`), и что JOIN здесь нет вообще — сервис
собирает объект в Go.

**Почему запросу не нужны другие шарды.**

Условие содержит shard key, поэтому router вычисляет адрес арифметически, до
обращения к базе: `hash(user_id)` → точка на кольце → шард. Это не поиск, а
вычисление, и оно однозначно: запись с данным `user_id` может лежать **только**
на этом шарде — именно туда её положил тот же router при вставке. Опрашивать
остальные бессмысленно: там её нет по построению.

Все три запроса `GetByID` попали в один шард, потому что `drivers`, `users` и
`vehicles` шардированы **одним и тем же** ключом. Профиль водителя, его машина
и его оценки физически лежат вместе — это co-location, и именно он сохраняет
такие эндпойнты дешёвыми.

С точки зрения нагрузки такой запрос — лучший случай: он занимает 1 из 4
шардов, значит кластер параллельно обслуживает четыре независимых запроса.

# 3. Агрегирующий запрос

## а) Агрегация, оставшаяся одношардовой

`RatingRepository.Create` после вставки оценки пересчитывает средний балл:

```go
tx.Model(&RatingModel{}).
   Where("ratee_id = ?", rating.RateeID).
   Select("COALESCE(AVG(score), 0)").Scan(&avg)
```

Через реальный `POST /v1/ratings`:

```text
   оценка водителю b4dc35bc... -> shard0    23.4 мс
   сервис вернул пересчитанный средний балл: {'new_average': 4.08866}
   INSERT + AVG + UPDATE прошли одной транзакцией на одном шарде
```

Тот же эффект на уровне SQL (замер напрямую в шардах):

```text
   ratee 9ab5e338... -> shard1  AVG=4.073 по 86 оценкам    36.0 мс
   ratee bc7585c4... -> shard3  AVG=3.901 по 83 оценкам    33.4 мс
```

Агрегат берётся по `ratee_id`, то есть по shard key. Все оценки водителя лежат
на его шарде, поэтому `AVG` считается локально — и вся транзакция
(INSERT + AVG + UPDATE users) остаётся в одной базе, сохраняя атомарность.
**Это ключевой аргумент в пользу `ratee_id` как ключа для `ratings`.**

## б) Агрегация по всему сервису

`GET /v1/drivers` без фильтра по пользователю — `GROUP BY status`:

```text
   shard0: offline=951, on_trip=960, available=896
   shard1: offline=758, on_trip=706, available=740
   shard2: on_trip=865, offline=841, available=838
   shard3: offline=835, on_trip=778, available=832
   -> слияние в приложении: available=3,306, offline=3,385, on_trip=3,309
   scatter-gather занял 126.7 мс
```

**1. Можно ли выполнить такой запрос только на одном shard?**
Нет. Водители распределены по всем четырём шардам, и ни один не содержит
полной картины. Ответ с одного шарда — не приближение, а просто четверть
данных.

**2. Где должны объединяться результаты?**
В приложении, в слое router. Шарды считают частичные агрегаты
(`count(*) GROUP BY status`), backend суммирует. Каждый агрегат требует своего
способа слияния:

| Агрегат | Как слить | Что запрашивать с шардов |
|---|---|---|
| `COUNT` | сумма | `count(*)` |
| `SUM` | сумма | `sum(x)` |
| `MIN`/`MAX` | минимум/максимум | `min(x)`/`max(x)` |
| `AVG` | **нельзя усреднять средние** | `sum(x)` и `count(*)` отдельно |
| `COUNT(DISTINCT)` | **нельзя суммировать** | сами значения либо HyperLogLog |

Ловушка с `AVG` проверена на реальных данных:

```text
   shard0: count= 56,774  sum= 226,971.0  avg=3.9978
   shard1: count= 43,187  sum= 172,680.1  avg=3.9984
   shard2: count= 51,352  sum= 205,504.8  avg=4.0019
   shard3: count= 48,687  sum= 194,814.0  avg=4.0013

   неверно (среднее из четырёх AVG): 3.999848
   верно   (sum(sum) / sum(count)):  3.999849
```

Здесь расхождение ничтожно — 0.000001, и это честный результат: оценки
распределены равномерно, а размеры шардов близки. Но величина ошибки зависит
от перекоса, и достаточно арифметического примера, чтобы увидеть масштаб: если
на shard0 лежит 1 оценка со счётом 5.0, а на shard1 — 99 999 оценок со счётом
4.0, то среднее средних даст `(5.0 + 4.0) / 2 = 4.5`, тогда как правильный
ответ — `4.00001`. Ошибка в полбалла на пустом месте. Поэтому `AVG` нужно
разбирать на `SUM` и `COUNT` всегда, а не только когда данные выглядят
перекошенными.

**3. Что происходит со временем выполнения при увеличении числа шардов?**

Замер одного и того же `COUNT(*) FROM ratings`:

| Шардов | Через REST API | Напрямую в SQL |
|---:|---:|---:|
| 1 | 22.4 мс | 33.2 мс |
| 2 | 41.8 мс | 64.4 мс |
| 3 | 65.0 мс | 98.8 мс |
| 4 | 81.7 мс | 128.4 мс |

Рост линейный, потому что в этой реализации router обходит шарды
последовательно: четыре шарда — четыре round-trip подряд. При параллельных
запросах время свелось бы к времени самого медленного шарда плюс слияние, то
есть росло бы примерно как максимум из N задержек — медленнее, но всё равно
не уменьшалось бы. Общее правило: распределённый агрегат никогда не быстрее
одношардового, он лишь позволяет обработать больше данных.

Важно и то, что каждый такой запрос занимает **все** шарды сразу. Пока он
выполняется, кластер обслуживает один запрос вместо четырёх — распределённые
агрегаты съедают ту самую пропускную способность, ради которой затевалось
шардирование.

# 4. JOIN между шардами

## а) JOIN, который остался локальным

```sql
SELECT d.user_id, u.name, v.plate_number
FROM drivers d
JOIN users u    ON u.id = d.user_id
LEFT JOIN vehicles v ON v.driver_id = d.user_id
WHERE d.status = 'available';
```

```text
   shard0: JOIN выполнен локально, строк 5
   shard1: JOIN выполнен локально, строк 5
   shard2: JOIN выполнен локально, строк 5
   shard3: JOIN выполнен локально, строк 5
   итого 20 строк за 121.8 мс, ни одной передачи между шардами
```

Все три таблицы шардированы по `user_id`, поэтому связанные строки гарантированно
лежат вместе, и обычный SQL JOIN работает внутри каждого шарда без изменений.

## б) JOIN, который стал распределённым

Показать оценки водителя вместе с именами тех, кто их поставил. В `ratings`
два пользовательских ключа: `ratee_id` (по нему шардируем) и `rater_id`
(посторонний). Профиль автора оценки лежит там, куда его определил хеш **его
собственного** id:

```text
   ratee 9ab5e338... живёт на shard1
      оценок получено:        10
      авторы разбросаны по:   shard0, shard1, shard2, shard3
      дополнительных запросов: 4 (вместо одного JOIN)
      суммарно 123.4 мс
```

Десять оценок — и авторы всех четырёх шардов.

**1. Что произойдёт, если связанные записи находятся на разных shard'ах?**
JOIN перестаёт быть операцией базы и становится обязанностью приложения.
Backend делает запрос на «домашний» шард, извлекает `rater_id`, группирует их
по шардам и делает дополнительный запрос на каждый задействованный шард, после
чего соединяет результаты в памяти. Вместо одного плана с `Hash Join` внутри
PostgreSQL получается несколько сетевых round-trip и ручная сборка.

**2. Можно ли выполнить такой JOIN обычным SQL-запросом к одному PostgreSQL?**
Нет. Каждый экземпляр видит только свои таблицы; `shard1` физически не знает о
строках `shard0`. Обойти это можно только внешними средствами — `postgres_fdw`
с внешними таблицами, распределённым слоем вроде Citus, или (как здесь)
логикой в приложении. Во всех вариантах данные всё равно едут по сети, вопрос
лишь в том, кто их везёт.

**3. Какие данные пришлось бы передавать между shard'ами?**
В этом сценарии — список `rater_id` (по 16 байт на UUID) туда и пары
`id → name` обратно. Это благополучный случай: справочная выборка по ключам.
Плохой случай — JOIN двух больших таблиц без ограничения: тогда пришлось бы
перегонять целые наборы строк, чтобы соединить их на одной стороне
(broadcast или repartition join). Объём трафика тогда сопоставим с размером
самих таблиц, и такой запрос из оперативного пути надо убирать.

**4. Можно ли выбрать shard key так, чтобы JOIN чаще выполнялся внутри одного
shard?**
Да, и на практике именно так и делают. Три приёма, все применимы к Triply-User:

- **Co-location по общему ключу.** Уже сделано: `users`, `riders`, `drivers`,
  `vehicles` и `ratings` шардированы по `user_id`, поэтому JOIN из пункта (а)
  локален. Это сознательный выбор ключа под главный запрос.
- **Выбор «правильного» из двух ключей.** У `ratings` их два. Шардирование по
  `ratee_id` делает локальными пересчёт рейтинга и список оценок водителя —
  то есть горячие пути. Шардирование по `rater_id` сделало бы локальным
  «мои оставленные оценки» — редкий сценарий. Выбор сделан в пользу частого.
- **Reference-таблицы.** Небольшие справочники (тарифы, категории, города)
  копируются целиком на каждый шард, и JOIN с ними всегда локален. Цена —
  синхронизация копий, поэтому так поступают только с редко меняющимися
  данными.

Полностью убрать распределённые JOIN нельзя: `ratings` связаны с двумя
пользователями сразу, а лежать в двух местах одна строка не может. Можно лишь
выбрать, какая сторона связи будет быстрой.

# 5. ORDER BY + LIMIT

**Запрос:** `GET /v1/drivers?status=available` → `DriverRepository.List`

```go
base().Order("drivers.created_at DESC, drivers.user_id DESC")
applyWindow(q, params)   // LIMIT/OFFSET
```

Shard key в условии отсутствует, поэтому запрос идёт на все шарды: с каждого
берётся top-20, результаты сливаются, отдаются первые 20.

Реальные вызовы `GET /v1/drivers?status=available&page_size=20` ко всем
четырём экземплярам:

```text
   shard0: вернул 20 кандидатов
   shard1: вернул 20 кандидатов
   shard2: вернул 20 кандидатов
   shard3: вернул 20 кандидатов

   правильный top-20 собран за 93.8 мс из:
      shard0: 7 из 20
      shard1: 5 из 20
      shard2: 2 из 20
      shard3: 6 из 20
```

**Почему недостаточно взять первые 100 (здесь — 20) записей с одного shard?**

Потому что глобальный порядок не совпадает ни с одним локальным. Правильный
ответ собрался из всех четырёх шардов в пропорции 7 / 5 / 2 / 6 — и заранее
неизвестно, какой шард сколько даст: это зависит от данных, а не от
конфигурации. Проверка на том же наборе:

```text
   если бы спросили только shard0:
      совпало: 7 из 20, пропущено: 13
```

Тринадцать из двадцати самых свежих водителей просто не попали бы в выдачу,
причём ответ выглядел бы совершенно правдоподобно — 20 строк, отсортированных
по дате. Это худший вид ошибки: молчаливо неверный результат.

Обязательное условие корректности: с каждого шарда нужно запросить **столько
же** строк, сколько требует итоговый `LIMIT`. Меньше нельзя — вдруг все 20
лучших лежат на одном шарде.

Отсюда же главная проблема пагинации: `LIMIT 20 OFFSET 10000` требует с
каждого шарда 10 020 строк, то есть 40 080 строк ради двадцати. Стоимость
растёт линейно с `OFFSET`, помноженная на число шардов. Лечится это переходом
на keyset-пагинацию (`WHERE created_at < $last_seen ORDER BY created_at DESC
LIMIT 20`), где с каждого шарда всегда берётся ровно 20 строк независимо от
глубины. В коде `applyWindow` сейчас использует `Offset`, и при шардировании
это первое место, которое придётся переписать.

# 6. Отказ одного shard

Эксперимент настоящий: `shard2` остановлен, затем поднят обратно.

**1. Какие данные становятся недоступны?**
Профили, машины и оценки тех пользователей, чей `hash(user_id)` указывает на
`shard2` — примерно четверть базы: 12 650 профилей, 2 544 водителя,
51 352 оценки. Остальные три четверти доступны полностью.

Эксперимент: остановлен PostgreSQL шарда `shard2`, при этом **экземпляр
сервиса на :8092 продолжает работать** — то есть отказала именно база, а не
приложение.

```text
1) Запрос к пользователю с упавшего шарда:
   GET /v1/drivers/bcf09afa... -> shard2: HTTP 500
   {"error":"internal","message":"failed to connect to `user=po..."}

2) Запросы к пользователям с живых шардов:
   b4dc35bc... -> shard0: OK, Driver 1618  22.1 мс
   73b2ea7a... -> shard1: OK, Driver 3611  28.5 мс
   20570d50... -> shard3: OK, Driver 6407  22.0 мс
```

Сервис отдаёт `500 internal` с текстом ошибки подключения — то есть наружу
утекает деталь инфраструктуры вместо честного `503 Service Unavailable` с
`Retry-After`. Это первое, что стоит поправить в обработке ошибок.

**2. Какие endpoint'ы перестанут работать?**

| Эндпойнт | Поведение при отказе shard2 |
|---|---|
| `GET /v1/drivers/{user_id}` | отказ только для «своих» user_id, для остальных работает |
| `GET /v1/riders/{user_id}` | то же |
| `PATCH /v1/drivers/{user_id}` | то же |
| `POST /v1/ratings` | отказ, если оценивают водителя с shard2 |
| `PUT /v1/drivers/{id}/availability` | отказ для водителей с shard2 |
| `GET /v1/drivers?status=` | **работает, но отдаёт неполный список** |
| `GET /v1/ratings` (без ratee_id) | **работает, но отдаёт неполный список** |

Опаснее всего последние две строки — они не падают, а тихо врут:

```text
3) Scatter-запрос по всем экземплярам:
   ответили: shard0=896, shard1=740, shard2=0, shard3=832
   сумма = 2,468 — это НЕПОЛНОЕ число, но сервис его отдал
   ошибок транспорта: 0 (экземпляр жив, падает только его запрос к БД)

   после восстановления сумма = 3,306
```

Особенно показательна строка `shard2=0`: экземпляр ответил `200 OK` с
`total: 0`. Для router это неотличимо от «на этом шарде просто нет свободных
водителей», поэтому неполнота не детектируется вообще.

После восстановления шарда тот же запрос даёт `available=3,306`. То есть во
время аварии сервис уверенно отдавал заниженное на четверть число, ничем не
отличимое от правды.

**3. Продолжит ли работать остальная часть сервиса?**
Да, и это принципиальное отличие шардирования от одной большой базы: отказ
одного узла выводит из строя ~25% пользователей, а не 100%. Запросы к живым
шардам обслуживались штатно (около 100 мс) всё время аварии.

**4. Что должен делать backend при обращении к недоступному shard?**

- **Быстро падать, а не висеть.** Короткий `connect_timeout` и circuit breaker.
  В Triply-User он уже есть — `internal/interface/grpc/interceptors/circuit_breaker.go`
  и его двойник в REST-middleware; его и надо применить на уровне шарда.
- **Возвращать честную ошибку** `503` с `Retry-After` для одношардовых
  запросов — пользователь должен понимать, что данные временно недоступны,
  а не думать, что профиль удалён.
- **Помечать неполноту** для scatter-запросов: либо ошибка, либо ответ с
  явным флагом `partial: true` и списком недоступных шардов. Молча отдавать
  частичный агрегат нельзя.
- **Не ретраить бесконечно** — отказ шарда обычно длится минуты, и лавина
  повторов только добьёт кластер.
- **Деградировать осознанно.** Для `GET /v1/drivers/{id}/availability` есть
  Redis-кеш с TTL 60 с — при недоступности шарда разумно отдать закешированное
  значение, отметив его как устаревшее.

**5. Как повысить отказоустойчивость?**
Поставить каждому шарду реплику — то есть соединить решения лабораторных №4
и №5: шардирование даёт масштаб, репликация — отказоустойчивость. Тогда при
падении Primary шарда его Replica продолжает обслуживать чтение, а после
failover принимает и запись. Дополнительно: автоматический failover
(Patroni), health-check шардов в router, чтобы не слать запросы в заведомо
мёртвый узел, и регулярные бэкапы каждого шарда по отдельности.

# 7. Hot Shard

Строк на шардах примерно поровну (разброс 27.17%). Вопрос в том, так же ли
распределяются **запросы**. Смоделировано 10 000 обращений в трёх сценариях.

## А. Много активных водителей: 20% дают 80% запросов

```text
   shard0   56,774 строк (28.39%)   2,647 запросов (26.47%)
   shard1   43,187 строк (21.59%)   2,026 запросов (20.26%)
   shard2   51,352 строк (25.68%)   2,743 запросов (27.43%)
   shard3   48,687 строк (24.34%)   2,584 запросов (25.84%)
   разброс по запросам: 28.68%
```

Горячего шарда **нет**. Хеш раскидал активных водителей по всем шардам, и их
нагрузка размазалась вместе с ними. Много горячих ключей — не проблема.

## Б. Один водитель собирает половину запросов

```text
   shard0   56,774 строк (28.39%)   1,299 запросов (12.99%)
   shard1   43,187 строк (21.59%)   5,997 запросов (59.97%)
   shard2   51,352 строк (25.68%)   1,407 запросов (14.07%)
   shard3   48,687 строк (24.34%)   1,297 запросов (12.97%)
   разброс по запросам: 188.00%
```

Вот он, hot shard: `shard1` принимает 59.97% трафика при 21.59% строк.
Распределение данных не изменилось ни на строку — изменился только профиль
запросов.

То же самое проверено **настоящими HTTP-вызовами**: 400 запросов
`GET /v1/drivers/{id}`, половина — к одному водителю.

```text
   шард       запросов      доля
   shard0          256     64.0%
   shard1           47     11.8%
   shard2           54     13.5%
   shard3           43     10.8%

   разброс нагрузки: 213.0%
```

Экземпляр сервиса на `shard0` обработал 64% всех HTTP-запросов, а три
остальных простаивали — при том что строк у них поровну.

## В. Запросы без shard key

`GET /v1/drivers?status=available` попадает в каждый шард, то есть даёт по 25%
нагрузки на все четыре одновременно. Чем выше доля таких запросов, тем меньше
смысла в шардировании: кластер работает как один узел, только медленнее.

## Почему равное количество строк ещё не означает равномерную нагрузку

Потому что хеш распределяет **ключи**, а нагрузку создают **запросы к ключам**,
и связи между этими величинами нет. Профиль водителя занимает одну строку
независимо от того, делают ли к нему один запрос в месяц или тысячу в минуту.

Конкретные причины перекоса в Triply-User:

- **Популярный ключ.** Водитель-«звезда» или корпоративный аккаунт: сценарий Б
  выше. Один ключ неделим — хеш физически не может разложить его по шардам.
- **Неудачный shard key.** Если бы шардировали по `status`, все `available`
  водители оказались бы на одном шарде, а именно к ним идёт основной трафик
  поиска машины.
- **Тип запроса.** Scatter-запросы нагружают все шарды сразу (сценарий В), а
  тяжёлая аналитика по одному пользователю — только его шард.
- **Перекос данных.** Водитель с 50 000 оценок делает и `AVG` по нему, и
  пагинацию его оценок дороже, чем у остальных, — при том же одном профиле.

# 8. Итоговый анализ shard key

**Подходит ли `user_id` для Triply-User? Да, это правильный выбор.**

Решающий довод: эндпойнты, которые вызываются на каждую поездку — получить
профиль, поставить оценку, обновить статус — остаются одношардовыми, а
распределёнными становятся административные и поисковые сценарии, которых
на порядки меньше.

## Плюсы: какие запросы стали эффективными

| Запрос | Почему дёшев |
|---|---|
| `GET /v1/drivers/{user_id}` | три таблицы co-located, один шард |
| `GET /v1/riders/{user_id}` | то же |
| `POST /v1/ratings` | вставка + `AVG(score)` + `UPDATE users` в одной транзакции на одном шарде |
| `GET /v1/ratings?ratee_id=` | все оценки водителя лежат вместе |
| `PUT /v1/drivers/{id}/availability` | точечное обновление |
| JOIN `drivers + users + vehicles` | остался обычным SQL JOIN |

Отдельно стоит отметить `POST /v1/ratings`: транзакция из трёх операций
осталась локальной. При другом ключе она стала бы распределённой, а это уже
двухфазный коммит со всеми его проблемами.

## Минусы: какие запросы стали распределёнными

| Запрос | Что происходит |
|---|---|
| `GET /v1/drivers?status=available` | scatter-gather по всем шардам + слияние |
| `GET /v1/ratings` без `ratee_id` | то же |
| любой `GROUP BY` по платформе | частичные агрегаты + слияние, 128.4 мс против 33.2 мс |
| оценки + профили авторов | 4 дополнительных запроса вместо одного JOIN |
| пагинация с `OFFSET` | с каждого шарда нужно `OFFSET + LIMIT` строк |
| уникальность `users.phone` | локальна для шарда, глобально не гарантируется |

Последняя строка — неочевидная, но важная: в модели стоит
`Phone string gorm:"uniqueIndex"`, и после шардирования этот индекс
защищает от дублей только внутри одного шарда. Два пользователя с одинаковым
телефоном на разных шардах создадутся без ошибки. Глобальную уникальность
придётся обеспечивать отдельно — например, шардируя по телефону отдельную
таблицу-реестр.

## Проблемные операции

| Операция | Сложность | Почему |
|---|---|---|
| **JOIN** | средняя | локален там, где co-location; распределён для `rater_id` |
| **Aggregation** | высокая | всегда scatter, время растёт с числом шардов, `AVG`/`DISTINCT` требуют переписывания |
| **ORDER BY + LIMIT** | высокая | нужен top-N с каждого шарда, `OFFSET` умножается на число шардов |
| **Migration** | высокая | при изменении числа шардов переезжает часть данных (в лабораторной №5 — 24.51% на кольце против 75.25% на модуле) |
| **Backup** | средняя | четыре независимых бэкапа вместо одного |
| **Восстановление** | **самая высокая** | бэкапы шардов сняты в разные моменты, согласованного на весь кластер состояния нет |
| **Балансировка** | высокая | горячий ключ не лечится хешем (сценарий Б), нужен ручной вынос |

Восстановление стоит выделить особо. Бэкап каждого шарда консистентен сам по
себе, но между шардами общей точки согласованности нет. Оценка, вставленная в
`ratings` на shard1, и `UPDATE users.rating` — если бы они оказались на разных
шардах — могли бы попасть в бэкапы разных моментов. В нашей схеме этот
конкретный случай спасён co-location, но для связей через `rater_id` проблема
остаётся в полной мере.

## Вывод: оставил бы ключ или выбрал другой?

**Оставил бы `user_id`.** Проектируя заново, я пришёл бы к тому же решению,
потому что в Triply-User нет ключа лучше: сервис по своей природе
пользовательский, и подавляющее большинство его операций адресуют конкретного
человека. Альтернативы очевидно хуже: `status` создал бы горячий шард из
`available` водителей; `city` — перекос в пользу Москвы; случайный ключ
разрушил бы co-location и сделал бы распределённым даже `GetByID`.

Но три вещи я бы сделал иначе с самого начала:

1. **Заменил бы `OFFSET` на keyset-пагинацию** в `applyWindow` ещё до
   шардирования — иначе глубокая пагинация умножает нагрузку на число шардов.
2. **Вынес бы поиск доступных водителей из PostgreSQL.** `GET /v1/drivers?status=available` —
   самый частый из scatter-запросов и главный кандидат на хот-путь в такси.
   Ему место в Redis (который в сервисе уже есть для availability) или в
   геоиндексе: водителей ищут по «рядом и свободен», а это не та задача, для
   которой нужен скан четырёх PostgreSQL.
3. **Заложил бы реплику на каждый шард сразу**, потому что после шардирования
   отказ одного узла — это уже не гипотеза, а регулярное событие: узлов
   четыре, и вероятность отказа хотя бы одного вчетверо выше.

# Вопросы для самопроверки

**1. Чем single-shard query отличается от distributed query?**
Single-shard содержит shard key, поэтому router вычисляет адрес арифметически
и отправляет запрос ровно в один экземпляр; результат готов сразу и кластер
параллельно обслуживает другие запросы. Distributed query не содержит shard
key: его приходится отправлять во все шарды и объединять ответы в приложении.
Замер: `GET /v1/drivers/{id}` — один шард, ~100 мс; `COUNT` по всем —
128.4 мс и все четыре шарда заняты.

**2. Почему JOIN между shard'ами сложнее обычного JOIN?**
Потому что PostgreSQL умеет соединять только те таблицы, которые видит.
Каждый шард знает лишь свои строки, поэтому соединение приходится делать в
приложении: запросить одну сторону, извлечь ключи, сгруппировать их по шардам,
сделать дополнительный запрос на каждый и собрать результат в памяти. Вместо
одного плана с `Hash Join` — несколько round-trip и ручная сборка; в замере
десять оценок потребовали четырёх дополнительных запросов.

**3. Как выполнить `COUNT(*)` по всем shard'ам?**
Отправить `SELECT count(*)` на каждый шард и сложить ответы — `COUNT`
складывается, потому что это сумма непересекающихся множеств. Важно, что так
можно не со всеми агрегатами: `AVG` требует отдельно `SUM` и `COUNT`, а
`COUNT(DISTINCT)` вообще нельзя сложить — нужны либо сами значения, либо
приближённый HyperLogLog.

**4. Почему `ORDER BY ... LIMIT` требует объединения результатов?**
Потому что глобальный порядок не совпадает с локальным ни на одном шарде.
В замере правильный top-20 собрался из всех четырёх шардов в пропорции
7 / 5 / 2 / 6, и заранее неизвестно, кто сколько даст. Взяв top-20 только с
shard0, мы получили бы 7 верных строк из 20 и потеряли 13 — при этом ответ
выглядел бы корректным. С каждого шарда нужно брать полный `LIMIT` строк.

**5. Что произойдёт при отказе одного shard?**
Станет недоступна его доля данных — в нашем случае ~25%: 12 650 профилей и
51 352 оценки. Запросы по ключам этого шарда падают, запросы к остальным
работают штатно (около 100 мс в замере). Опаснее всего scatter-запросы: они не
падают, а возвращают неполный результат — во время аварии сервис отдавал
`available=2,468` вместо `3,306`, никак не сигнализируя о неполноте.

**6. Что такое hot shard?**
Шард, принимающий непропорционально большую долю нагрузки. В эксперименте
`shard1` получил 59.97% запросов при 21.59% строк из-за одного популярного
водителя. Ключевое: распределение данных при этом идеально ровное — хеш
распределяет ключи, а не запросы к ним, и один ключ неделим.

**7. Почему выбор shard key влияет на JOIN?**
Потому что JOIN локален ровно тогда, когда обе соединяемые строки лежат на
одном шарде, а это определяется ключом. `users`, `drivers` и `vehicles`
шардированы по `user_id`, поэтому их JOIN остался обычным SQL. А `ratings`
связаны с двумя пользователями сразу: по `ratee_id` они co-located, по
`rater_id` — нет, и тот же логический JOIN становится распределённым.

**8. Какие операции особенно плохо подходят для распределённых данных?**
Агрегация по всем данным, `ORDER BY` с глубоким `OFFSET`, `COUNT(DISTINCT)`,
JOIN больших таблиц по неключевому полю, глобальные ограничения уникальности
и транзакции, затрагивающие несколько шардов (требуют двухфазного коммита).
Общая черта: все они требуют видеть весь набор данных сразу, а шардирование
именно это и запрещает.

**9. Что произойдёт при изменении количества shard'ов?**
Изменится отображение ключей на шарды, и часть данных придётся физически
перенести. Насколько большая — зависит от стратегии: в лабораторной №5
переход 3 → 4 шарда переместил 75.25% записей при `hash(key) % N` и 24.51%
при consistent hashing. Во время переноса система должна оставаться
работоспособной, что требует отдельного механизма двойной записи или
read-only окна.

**10. Чем шардирование отличается от репликации?**
Репликация хранит **одни и те же** данные на нескольких узлах — это
отказоустойчивость и масштабирование чтения; отказ узла не теряет данных.
Шардирование хранит **разные** данные на разных узлах — это масштабирование
объёма и записи; отказ узла делает его долю недоступной. Они решают разные
задачи и хорошо сочетаются: реплика у каждого шарда даёт и масштаб, и
устойчивость.

**11. Может ли шардирование сделать отдельный SQL-запрос быстрее?**
Косвенно — да, но не само по себе. Отдельный запрос ускоряется лишь потому,
что таблица на шарде меньше: индекс ниже, данные лучше помещаются в кеш.
Это тот же эффект, что от партиционирования, и он ограничен. Распределённый
же запрос шардирование **замедляет**: `COUNT` по всем данным вырос с 33.2 мс
на одном шарде до 128.4 мс на четырёх. Шардирование масштабирует не скорость
одного запроса, а способность системы обслуживать больше запросов и хранить
больше данных.
