# Лабораторная работа №5. Шардирование: Router и Consistent Hashing

Распределение данных сервиса CarRent между четырьмя независимыми экземплярами
PostgreSQL и сравнение двух стратегий маршрутизации при изменении числа шардов.

Все числа получены на живом стенде, записи при ресшардинге переносятся
физически. Полный протокол — конфигурация, код и вывод — в
[`result5.md`](result5.md), сырой вывод — в `lab5/results/lab5_raw.txt`.

## Условия эксперимента

| Параметр | Значение |

| Шарды | 4 независимых PostgreSQL 18 (`lab5_shard0..3`, порты 5440-5443) |

Стенды предыдущих работ лежат в `docker-compose3.yaml` (партиционирование) и

# 1. Выбор данных для шардирования

**1. Какую сущность выбрали?**
`rentals` — факт аренды автомобиля пользователем. Это центральная
транзакционная таблица CarRent: `cars`, `users`, `car_categories` —
справочники, ограниченные размером автопарка и клиентской базы, а `rentals`
растёт всё время, пока сервис работает. В лабораторной №2 именно она показала
линейный рост времени запросов, а в №3 её пришлось партиционировать.

**2. Какое поле используется как shard key?**
`user_id`.

**3. Почему выбран именно этот ключ?**
Три причины.

Во-первых, по нему идут основные запросы сервиса. История аренд, личный
кабинет, проверка активной аренды — всё это `WHERE user_id = ?`. Запрос с
известным shard key обслуживается **одним** шардом, а не всеми четырьмя.

Во-вторых, он обеспечивает локальность данных: все аренды одного пользователя
физически лежат вместе, поэтому выборка истории не превращается в
scatter-gather по всем экземплярам с последующим слиянием на стороне сервиса.

В-третьих, `user_id` неизменен. Шардировать по изменяемому полю (например, по
статусу аренды) нельзя: при каждом обновлении запись пришлось бы физически
переносить между экземплярами.

Альтернативы хуже. `id` аренды дал бы идеальную равномерность, но тогда
история одного пользователя размазалась бы по всем шардам. `car_id` разрушил
бы главный пользовательский сценарий. `created_at` создал бы «горячий» шард:
весь текущий трафик писался бы в один экземпляр.

**4. Насколько равномерно ключ распределяет данные?**
Само по себе значение `user_id` распределено неравномерно — активные
пользователи ездят чаще. В сгенерированном наборе на 100 000 аренд приходится
19 556 различных пользователей, а у самых активных — по 47 аренд. Но
распределяет данные не сам ключ, а его **хеш**: md5 «размазывает» даже
перекошенные значения. Фактический результат — отклонение шардов от идеала в
пределах 1.31% (см. задание 4).

Ограничение принципиальное: хеш выравнивает распределение по *количеству
ключей*, но не по *нагрузке на ключ*. Если один корпоративный клиент начнёт
делать половину всех аренд, его шард станет горячим, и никакой хеш этого не
исправит (см. вопрос 10).

**5. Какие запросы сервиса используют этот ключ?**

| Эндпойнт | SQL | Шардов задействовано |
|---|---|---|
| `GET /rentals?user_id=` | `WHERE user_id = $1 ORDER BY started_at DESC` | 1 |
| `POST /rentals` | `INSERT ... (user_id, ...)` | 1 |
| `GET /users/{id}/active` | `WHERE user_id = $1 AND finished_at IS NULL` | 1 |
| `GET /rentals/statistics` | агрегат по всем арендам | **все** |

Последняя строка — честная цена шардирования: аналитика по всему сервису
теряет возможность выполниться одним запросом и требует обхода всех шардов с
последующим слиянием результатов.

Ключевое отличие от лабораторной №4: **между шардами нет никакой связи**. Это
не Primary и Replica, у них нет общего WAL и они не знают о существовании друг
друга. Каждый хранит свою часть данных, а знание о том, где что лежит, живёт
только в router на стороне сервиса. Четвёртый экземпляр поднят сразу, но в
router добавляется лишь на этапе ресшардинга.

Схема на всех шардах одна и та же:

```sql
CREATE TABLE rentals (
    id          BIGINT       PRIMARY KEY,
    user_id     BIGINT       NOT NULL,
    car_id      BIGINT       NOT NULL,
    started_at  TIMESTAMPTZ  NOT NULL,
    finished_at TIMESTAMPTZ,
    minute_fee  NUMERIC(8,2) NOT NULL
);
CREATE INDEX idx_rentals_user ON rentals (user_id, started_at DESC);
```

Индекс внутри шарда нужен по-прежнему: шардирование убирает лишние *шарды*,
индекс — лишние *строки* внутри оставшегося.

# 3. Реализация простого Router

```python
class ModuloRouter:
    """shard = hash(key) % N — простейшая стратегия."""

    def __init__(self, shards: list[str]):
        self.shards = list(shards)

    def route(self, key) -> str:
        return self.shards[stable_hash(key) % len(self.shards)]
```

Сервис не обращается к экземплярам напрямую — он спрашивает router:

```python
class ShardRouter:
    def shard_for(self, user_id: int) -> str:
        return self.strategy.route(user_id)         # ключ -> имя шарда

    def create_rental(self, rental: dict) -> str:
        shard = self.shard_for(rental["user_id"])   # POST /rentals
        shards.query(shard, "INSERT INTO rentals ...")

    def user_rentals(self, user_id: int):
        shard = self.shard_for(user_id)             # GET /rentals?user_id=
        return shards.query(shard, "SELECT ... WHERE user_id = ...")
```

## Почему не встроенная `hash()`

Существенная деталь реализации: в Python `hash()` от строки рандомизируется
при каждом запуске процесса (`PYTHONHASHSEED`). Router на такой функции
работал бы до первого перезапуска сервиса, после чего тот же `user_id`
поехал бы на другой шард, а данные остались бы на старом. Поэтому взята
детерминированная функция:

```python
def stable_hash(value) -> int:
    digest = hashlib.md5(str(value).encode("utf-8")).digest()
    return int.from_bytes(digest[:8], "big")
```

Криптостойкость здесь не нужна — нужны воспроизводимость между процессами и
равномерность выходных значений.

Пример маршрутизации (реальный вывод):

```text
hash(101) % 3 -> shard1
hash(102) % 3 -> shard2
hash(103) % 3 -> shard1
```

# 4. Распределение данных

Загружено 100 000 аренд на три шарда:

| Шард | Записей | Доля | Отклонение от идеала |
|---|---:|---:|---:|
| shard0 | 32 896 | 32.90% | −1.31% |
| shard1 | 33 368 | 33.37% | +0.10% |
| shard2 | 33 736 | 33.74% | +1.21% |
| **итого** | **100 000** | | |

Разброс между самым большим и самым маленьким шардом — **2.52%** от идеала.

Счётчики прочитаны из самих PostgreSQL и сошлись с расчётом router; кроме
того, 2 000 случайных записей проверены на то, что router находит их именно на
предсказанном шарде.

**Насколько равномерно распределились данные?** Практически идеально:
отклонение не превышает 1.31% при заметно неравномерном исходном
распределении `user_id` (у активных пользователей по 47 аренд против одной у
большинства). Хеш-функция сделала своё дело.

**Есть ли заметный дисбаланс?** На этих данных — нет.

**Может ли такой дисбаланс стать проблемой?** Разброс в 2.5% — нет. Но
равномерность по числу записей не означает равномерности по нагрузке.
Проблемой станет не перекос счётчиков, а «горячий» ключ: один корпоративный
клиент с десятками тысяч аренд создаст на своём шарде и объём, и трафик,
которых нет на других. Хеширование от этого не спасает — оно распределяет
ключи, а не запросы к ним.

# 5. Что произойдёт при добавлении нового shard?

Переход `hash(key) % 3` → `hash(key) % 4` на тех же 100 000 записях:

```text
остаются на месте: 24 752
меняют шард:       75 248  (75.25%)
```

| | Записей | Доля |
|---|---:|---:|
| Изменили шард | 75 248 | **75.25%** |
| Не изменили | 24 752 | 24.75% |

Показательны сами потоки переноса — задействованы **все девять** возможных
направлений, а не только «в новый шард»:

```text
   shard0 -> shard1: 8 109      shard1 -> shard0: 8 303      shard2 -> shard0: 8 373
   shard0 -> shard2: 8 079      shard1 -> shard2: 8 431      shard2 -> shard1: 8 640
   shard0 -> shard3: 8 301      shard1 -> shard3: 8 305      shard2 -> shard3: 8 707
```

Физический перенос 75 248 записей занял 4.7 с. Итоговое распределение снова
ровное (разброс 3.15%), суммарное число записей не изменилось.

**Почему добавление одного PostgreSQL приводит к перемещению такого объёма?**

Потому что в формуле `hash(key) % N` число `N` входит в вычисление для
**каждого** ключа. Меняя `N`, мы меняем не «границу» между шардами, а саму
функцию отображения целиком: остаток от деления на 3 и остаток от деления на 4
никак не связаны. Запись остаётся на месте только по случайному совпадению
двух остатков — вероятность этого примерно `1/4`, что и даёт наблюдаемые
~75% переезжающих.

В теории при переходе `N → N+1` перемещать нужно всего `1/(N+1)` данных: ровно
столько, сколько должно достаться новому шарду. Модульная стратегия
перемещает в три раза больше — она вынуждает данные мигрировать ещё и между
старыми шардами, которые вообще не должны были меняться.

Для продакшена это означает: 75% базы читается, передаётся по сети и
перезаписывается. На объёме CarRent в десятки миллионов аренд это часы работы,
всё это время данные существуют в двух местах, и требуется отдельный механизм
поддержания консистентности на время миграции.

# 6. Реализация Consistent Hashing

Каждый шард представлен на кольце не одной точкой, а `vnodes` точками
(виртуальными узлами). Ключ отображается в точку кольца и обслуживается первым
шардом по часовой стрелке:

```python
class ConsistentHashRing:
    def __init__(self, shards, vnodes: int = 150):
        self.vnodes = vnodes
        self._points: list[int] = []       # отсортированные позиции на кольце
        self._owners: dict[int, str] = {}  # позиция -> шард
        for shard in shards:
            self.add_shard(shard)

    def _vnode_points(self, shard: str):
        for i in range(self.vnodes):
            yield stable_hash(f"{shard}#{i}")

    def add_shard(self, shard: str) -> None:
        self.shards.append(shard)
        for point in self._vnode_points(shard):
            self._owners[point] = shard
            bisect.insort(self._points, point)

    def route(self, key) -> str:
        h = stable_hash(key)
        idx = bisect.bisect_right(self._points, h)
        if idx == len(self._points):   # прошли конец кольца — возвращаемся в начало
            idx = 0
        return self._owners[self._points[idx]]
```

Три шарда по 150 виртуальных узлов дают 450 точек на кольце. Поиск — двоичный,
`O(log n)`; добавление шарда не трогает позиции остальных.

# 7. Сравнение стратегий

Переход `3 шарда → 4 шарда` на одних и тех же 100 000 записях:

| Стратегия | Перемещено | Доля | Время переноса |
|---|---:|---:|---:|
| `hash(key) % N` | 75 248 | **75.25%** | 4.7 с |
| Consistent Hashing | 24 506 | **24.51%** | 1.4 с |

Consistent hashing перемещает в **3.1 раза** меньше данных и попадает
практически в теоретический минимум (25.00%).

Разница видна и в структуре переносов. У кольца задействованы только три
направления — все в новый шард:

```text
   shard0 -> shard3: 6 540
   shard1 -> shard3: 9 556
   shard2 -> shard3: 8 410
```

Между старыми шардами не переехала ни одна запись.

**1. Почему результаты отличаются?**
В `hash(key) % N` число шардов входит в вычисление для каждого ключа, поэтому
изменение `N` переопределяет расположение всех записей сразу. В consistent
hashing позиции ключей и существующих шардов на кольце **не зависят** от числа
шардов: `hash(key)` и `hash("shard0#7")` остаются теми же. Новый шард лишь
вставляет свои точки в кольцо и забирает участки, которые к ним примыкают.

**2. Почему Consistent Hashing уменьшает объём перемещаемых данных?**
Потому что он делает границы владения **локальными**. Новый шард отбирает
только те отрезки кольца, которые оказались непосредственно перед его
виртуальными узлами; все остальные отрезки сохраняют прежних владельцев.
Переезжает примерно `1/(N+1)` данных — ровно та доля, которая и должна
достаться новичку, и ни записью больше.

**3. Что произойдёт, если добавить ещё один shard?**
Измерено на тех же ключах:

| Переход | `hash(key) % N` | Consistent Hashing | Теоретический минимум |
|---|---:|---:|---:|
| 3 → 4 | 75.25% | 24.51% | 25.00% |
| 4 → 5 | 80.00% | 17.27% | 20.00% |
| 5 → 6 | 83.50% | 15.43% | 16.67% |
| 6 → 7 | 85.92% | 14.16% | 14.29% |
| 7 → 8 | 87.73% | 11.79% | 12.50% |

Модульная стратегия с ростом кластера становится **хуже**: чем больше шардов,
тем меньше шанс, что остаток совпадёт, и тем ближе доля переезжающих к 100%.
Кольцо ведёт себя ровно наоборот — доля падает как `1/(N+1)`, то есть каждое
следующее расширение обходится дешевле предыдущего.

**4. Что произойдёт, если удалить shard?**
Выводим `shard2` из трёх:

```text
   записей жило на shard2:      33 736 (33.74%)
   hash(key) % N  переезжает:   66 880 (66.88%)
   Consistent Hashing:          33 194 (33.19%)
```

У кольца переезжают **только** записи удалённого шарда — их подбирают соседи
по кольцу, остальные данные не трогаются. Модульная стратегия снова
переопределяет расположение почти всех записей: переезжает вдвое больше, чем
физически лежало на выбывшем шарде.

## Цена, о которой стоит сказать прямо

Consistent hashing выигрывает по объёму миграции, но проигрывает по
равномерности — и после добавления шарда разрыв увеличивается:

| | `hash(key) % N` | Consistent Hashing |
|---|---:|---:|
| Разброс на 3 шардах | 2.52% | 8.28% |
| Разброс на 4 шардах | 3.15% | **23.10%** |

После расширения кольцо дало 28 243 записи на `shard0` против 22 467 на
`shard1` — разница в четверть. Лечится это увеличением числа виртуальных
узлов:

| vnodes | Разброс между шардами |
|---:|---:|
| 1 | 242.72% |
| 5 | 67.25% |
| 20 | 63.53% |
| 50 | 21.35% |
| 150 | 8.28% |
| 500 | 4.42% |

При одном узле на шард кольцо непригодно: разброс 242%, то есть шарды
отличаются в разы. Рост числа виртуальных узлов быстро выправляет картину и
при 500 приближается к качеству модульной стратегии. Плата — память и время
поиска: 500 узлов на шард при 100 шардах дают 50 000 точек в кольце.

# 8. Итог

**Shard** — отдельный независимый экземпляр базы, хранящий часть данных.
В этой работе четыре PostgreSQL, которые ничего не знают друг о друге: у них
нет общего WAL, как у Primary и Replica в лабораторной №4, и каждый хранит
свой кусок таблицы `rentals`. **Shard key** — поле, по которому вычисляется
расположение записи; здесь это `user_id`, выбранный потому, что по нему идут
основные запросы сервиса, он неизменен и обеспечивает локальность истории
пользователя. Знание о том, где что лежит, не хранится в базах, поэтому нужен
**router**: он превращает shard key в адрес конкретного экземпляра, и без него
сервис не знает, куда обращаться. Простейшая реализация — `hash(key) % N`: она
дала отличную равномерность (разброс 2.52%), но у неё есть фатальный
недостаток при изменении `N`. Поскольку число шардов участвует в вычислении
для каждого ключа, добавление четвёртого экземпляра переместило **75.25%**
записей, причём между всеми девятью парами шардов, хотя новому должно было
достаться лишь 25%. **Consistent hashing** решает это, делая границы владения
локальными: позиции ключей и существующих шардов на кольце не зависят от их
количества, поэтому новый шард забирает только примыкающие к его виртуальным
узлам участки — измеренные **24.51%** против теоретического минимума в 25%, и
ни одной записи между старыми шардами. С ростом кластера разрыв только растёт:
на переходе 7 → 8 это 87.73% против 11.79%, а при удалении шарда — 66.88%
против 33.19%. Плата за это — менее ровное распределение (23.10% разброса
против 3.15% после расширения), которое выправляется числом виртуальных узлов.

**Для CarRent я бы выбрал consistent hashing с 500 виртуальными узлами на
шард.** Решающий аргумент — не разовая экономия при миграции, а то, что
модульная стратегия делает расширение кластера практически невозможной
операцией: на реальном объёме аренд перенос 75-88% базы означает многочасовое
окно, в течение которого данные живут в двух местах. Кольцо сводит эту
операцию к переносу доли `1/(N+1)`, а его слабое место — неравномерность —
устраняется настройкой, которая ничего не стоит, кроме памяти под точки
кольца. При этом на старте, пока число шардов фиксировано и расширение не
планируется, `hash(key) % N` полностью достаточен и проще в отладке.

# Вопросы для самопроверки

**1. Что такое shard?**
Отдельный независимый экземпляр базы данных, хранящий часть общего набора
данных. Шарды не связаны между собой: в этой работе четыре PostgreSQL, каждый
со своей таблицей `rentals`, без общего журнала и без знания друг о друге.
Этим шардирование отличается от репликации, где все узлы хранят одно и то же.

**2. Что такое shard key?**
Поле записи, по которому вычисляется её расположение. Здесь — `user_id`.
Хороший shard key обладает тремя свойствами: он участвует в большинстве
запросов (иначе запрос придётся отправлять на все шарды), он неизменен (иначе
обновление поля потребует физического переноса записи) и его значения дают
достаточно ключей для равномерного распределения.

**3. Почему нельзя просто случайно распределять записи между PostgreSQL?**
Потому что тогда никто не будет знать, где лежит конкретная запись. Любое
чтение по `user_id` пришлось бы отправлять на **все** шарды и объединять
результаты, то есть каждый запрос нагружал бы весь кластер — ровно
противоположность тому, ради чего шардирование затевается. Расположение записи
должно вычисляться из её ключа детерминированно, без обращения к базе.

**4. Как работает `hash(key) % N`?**
Ключ пропускается через хеш-функцию, дающую равномерно распределённое число,
а остаток от деления на число шардов задаёт индекс шарда. Хеш нужен именно для
выравнивания: сами значения `user_id` распределены неравномерно, а их md5 —
равномерно, что и дало разброс в 2.52%. Функция должна быть детерминированной:
встроенная `hash()` в Python для строк рандомизируется при каждом запуске
процесса и для шардирования непригодна.

**5. Почему изменение количества shard'ов является проблемой?**
Потому что `N` входит в вычисление для каждого ключа, и его изменение
переопределяет расположение всех записей разом. Остаток от деления на 3 и на 4
не связаны между собой, поэтому запись остаётся на месте лишь по случайному
совпадению. Измерено: добавление одного шарда к трём переместило 75.25% данных
вместо необходимых 25%, задействовав все девять направлений переноса.

**6. Что такое Consistent Hash Ring?**
Пространство хешей, замкнутое в кольцо. И ключи, и шарды отображаются в точки
этого кольца одной и той же хеш-функцией; ключ обслуживает первый шард,
встреченный при движении по часовой стрелке. Каждый шард присутствует на
кольце многократно — виртуальными узлами. Поиск владельца — двоичный по
отсортированному массиву точек, `O(log n)`.

**7. Почему при добавлении shard'а не приходится переносить все данные?**
Потому что позиции ключей и уже существующих шардов на кольце не зависят от
их количества: `hash(user_id)` и `hash("shard0#7")` не меняются от появления
нового участника. Новый шард лишь вставляет свои точки и забирает участки
кольца непосредственно перед ними. Все остальные участки сохраняют прежних
владельцев — в эксперименте между старыми шардами не переехала ни одна запись.

**8. Что такое virtual nodes и зачем они нужны?**
Это несколько точек на кольце, представляющих один физический шард (здесь —
150 на шард, всего 450 точек при трёх шардах). Без них шард занимал бы на
кольце один случайный отрезок, и размеры отрезков различались бы в разы.
Измерено: при одном узле на шард разброс составил 242.72%, при 50 — 21.35%,
при 150 — 8.28%, при 500 — 4.42%. Виртуальные узлы также сглаживают
последствия вывода шарда: его нагрузка расходится по многим соседям, а не
падает целиком на одного.

**9. Может ли Consistent Hashing гарантировать идеальное распределение
нагрузки?**
Нет. Даже при 500 виртуальных узлах остаётся разброс 4.42%, потому что позиции
узлов случайны, и отрезки кольца никогда не будут равными. Более того, речь
идёт лишь о распределении *ключей*: consistent hashing ничего не знает о том,
сколько запросов приходится на каждый ключ и сколько данных за ним стоит.
Идеальное распределение даёт только явная карта диапазонов
(directory-based sharding), но она требует хранить и поддерживать саму карту.

**10. Что произойдёт, если один shard станет значительно более загруженным?**
Он превратится в узкое место: его задержки станут задержками всего сервиса
для части пользователей, при этом остальные шарды будут простаивать.
Типичная причина — «горячий» ключ: в CarRent это корпоративный клиент с
десятками тысяч аренд, все из которых по определению лежат на одном шарде,
потому что shard key у них общий. Хеширование здесь не помогает: оно
распределяет ключи, а один ключ неделим.

Варианты решения: добавить шарду больше виртуальных узлов (поможет от
случайного перекоса, но не от горячего ключа); вынести проблемного клиента на
отдельный выделенный шард; сделать составной shard key вроде
`user_id + месяц`, разбив историю одного пользователя на части (ценой того,
что запрос всей истории станет обращаться к нескольким шардам); либо поставить
перед шардом реплику для чтения, вернувшись к решению из лабораторной №4.
