# Лабораторная работа №4. Масштабирование чтения: Primary + Replica

Streaming replication между двумя экземплярами PostgreSQL, разделение
операций сервиса на запись и чтение, наблюдение replication lag.

Все результаты получены на живом стенде. Полный протокол — конфигурация,
запросы к обоим узлам и фактический вывод — в [`result4.md`](result4.md),
сырой вывод скрипта — в `lab4/results/lab4_raw.txt`.

## Условия эксперимента

| Параметр | Значение |
|---|---|
| СУБД | PostgreSQL 18 (образ `postgres:18`) |
| Primary | контейнер `lab4_primary`, порт **5432** |
| Replica | контейнер `lab4_replica`, порт **5433** |
| Тип репликации | физическая, streaming, асинхронная |
| Слот репликации | `replica_slot` (physical) |
| Сервис | CarRent, схема `carrent` |
| Данные | 5 000 пользователей, 1 000 машин, 200 000 аренд (позже 600 000) |

Стенд лабораторной №4 живёт в `docker-compose.yaml`; конфигурация
лабораторной №3 (партиционирование, pg_cron, alert-система) перенесена в
`docker-compose3.yaml` и здесь не участвует.

### Воспроизведение

```bash
docker compose --env-file ./.env up -d          # Primary + Replica
psql -h 127.0.0.1 -p 5432 -U postgres -f lab4/sql/01_carrent_schema.sql
./lab4/run_lab4.sh                              # части 1-6
python3 lab4/make_result4.py                    # пересборка result4.md
```

# Часть 1. Primary и Replica

## Фрагмент `docker-compose.yaml`

```yaml
services:
  postgres_primary:
    container_name: lab4_primary
    image: postgres:18
    environment:
      POSTGRES_USER: ${DB_USERNAME?error}
      POSTGRES_PASSWORD: ${DB_PASSWORD?error}
      POSTGRES_DB: ${DB_DATABASE?error}
      REPLICATION_USER: ${REPLICATION_USER:-replicator}
      REPLICATION_PASSWORD: ${REPLICATION_PASSWORD?error}
    command:
      - postgres
      - -c
      - wal_level=replica          # минимум для физической репликации
      - -c
      - max_wal_senders=10         # сколько реплик может читать WAL
      - -c
      - max_replication_slots=10
      - -c
      - hot_standby=on
    volumes:
      - primary_data:/var/lib/postgresql
      - ./docker/primary-init:/docker-entrypoint-initdb.d:ro
    ports:
      - "5432:5432"

  postgres_replica:
    container_name: lab4_replica
    image: postgres:18
    environment:
      PRIMARY_HOST: postgres_primary
      REPLICATION_USER: ${REPLICATION_USER:-replicator}
      REPLICATION_PASSWORD: ${REPLICATION_PASSWORD?error}
      REPLICATION_SLOT: ${REPLICATION_SLOT:-replica_slot}
      PGDATA: /var/lib/postgresql/18/docker
    user: postgres
    entrypoint: ["/usr/local/bin/replica-entrypoint.sh"]
    depends_on:
      postgres_primary:
        condition: service_healthy
    volumes:
      - replica_data:/var/lib/postgresql
      - ./docker/replica-entrypoint.sh:/usr/local/bin/replica-entrypoint.sh:ro
    ports:
      - "5433:5432"
```

## Кто есть кто

Роль узла определяется не именем контейнера, а функцией
`pg_is_in_recovery()`: реплика постоянно находится в режиме восстановления,
непрерывно применяя WAL.

```text
[PRIMARY] SELECT pg_is_in_recovery() ...
 in_recovery |  role   |                 version
-------------+---------+------------------------------------------
 f           | PRIMARY | PostgreSQL 18.0 (Debian 18.0-1.pgdg13+3)

[REPLICA] SELECT pg_is_in_recovery() ...
 in_recovery |  role
-------------+---------
 t           | REPLICA
```

(Колонка `inet_server_addr()` пуста, потому что `psql` внутри контейнера
подключается через Unix-сокет. Сетевой адрес реплики виден на Primary —
в `client_addr` таблицы `pg_stat_replication`, см. часть 2.)

## Как подключиться

| Узел | Изнутри сети Docker | С хоста |
|---|---|---|
| Primary | `postgres_primary:5432` | `psql -h 127.0.0.1 -p 5432 -U postgres` |
| Replica | `postgres_replica:5432` | `psql -h 127.0.0.1 -p 5433 -U postgres` |

Практическая деталь: с хоста нужно указывать именно `127.0.0.1`, а не
`localhost`. `localhost` в этой системе резолвится сначала в IPv6-адрес `::1`,
и проброс порта Docker по IPv6 не отвечает. Ошибки при этом не возникает:
`psql` молча ждёт TCP-таймаута, и только потом переключается на IPv4 и
подключается успешно. Внешне это выглядит как зависший на десятки минут
запрос — именно так и повёл себя первый запуск сервиса в этой работе.
Поэтому в `lab4/app/db.py` адрес `127.0.0.1` задан по умолчанию, а не
`localhost`.

# Часть 2. Настройка streaming replication

## Что сделано на Primary

Скрипт `docker/primary-init/00-replication.sh` выполняется один раз, при
создании пустого кластера, и делает две вещи:

```bash
# Отдельная роль только для репликации: атрибут REPLICATION даёт право
# читать поток WAL, но не даёт доступа к данным.
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD '...';

# Обычные строки pg_hba разрешают подключение к базам, но НЕ к псевдобазе
# replication — для неё нужна отдельная запись.
host    replication     replicator    all     scram-sha-256
```

Параметры сервера заданы в `command` (см. часть 1). Фактическое состояние:

```text
         name          | setting
-----------------------+---------
 hot_standby           | on
 max_replication_slots | 10
 max_wal_senders       | 10
 wal_level             | replica
```

## Что сделано на Replica

`docker/replica-entrypoint.sh` при первом старте снимает базовую копию:

```bash
pg_basebackup \
    --host=postgres_primary --username=replicator \
    --pgdata="$PGDATA" --format=plain \
    --wal-method=stream \          # тянуть WAL параллельно с копированием
    --write-recovery-conf \        # создать standby.signal и primary_conninfo
    --create-slot --slot=replica_slot
```

Лог первого запуска:

```text
[replica] каталог данных пуст — ждём Primary на postgres_primary
[replica] снимаем базовую копию через pg_basebackup
pg_basebackup: initiating base backup, waiting for checkpoint to complete
pg_basebackup: write-ahead log start point: 0/2000028 on timeline 1
pg_basebackup: starting background WAL receiver
pg_basebackup: created replication slot "replica_slot"
pg_basebackup: base backup completed
```

При последующих запусках копия уже есть, и реплика просто догоняет Primary
по WAL с того места, где остановилась.

## Цепочка передачи изменений

```
Primary                                   Replica
  INSERT/UPDATE
      │
      ├─► запись в WAL (журнал предзаписи)
      │
      └─► walsender ──── поток WAL по TCP ───► walreceiver
                                                   │
                                                   ├─► запись WAL на диск
                                                   │
                                                   └─► startup process
                                                       применяет записи
                                                       к файлам данных
```

## Состояние репликации

`pg_stat_replication` на Primary — взгляд со стороны отправителя:

```text
 client_addr |  usename   | application_name |   state   | sync_state |  sent_lsn  | replay_lsn |   replay_lag
-------------+------------+------------------+-----------+------------+------------+------------+-----------------
 172.2.0.4   | replicator | walreceiver      | streaming | async      | 0/304269C8 | 0/304269C8 | 00:00:00.041135
```

`pg_stat_wal_receiver` на Replica — взгляд со стороны получателя:

```text
  status   |   sender_host    | sender_port |  slot_name   | written_lsn | flushed_lsn | latest_end_lsn
-----------+------------------+-------------+--------------+-------------+-------------+----------------
 streaming | postgres_primary |        5432 | replica_slot | 0/30426A28  | 0/30426A28  | 0/30426A28
```

Слот репликации:

```text
  slot_name   | slot_type | active | restart_lsn | wal_status
--------------+-----------+--------+-------------+------------
 replica_slot | physical  | t      | 0/304269C8  | reserved
```

Слот важен практически: он запрещает Primary удалять сегменты WAL, которые
реплика ещё не забрала. Без слота реплика, отставшая или отключённая надолго,
рискует не найти нужный WAL и потребует повторного `pg_basebackup`. Обратная
сторона — если реплика умерла насовсем, а слот остался, WAL будет копиться,
пока не кончится диск.

Строка подключения реплики (пароль замаскирован):

```text
user=replicator password=*** host=postgres_primary port=5432 sslmode=prefer ...
```

# Часть 3. Доказательство, что репликация работает

## Запись на Primary

```sql
INSERT INTO users (name, email)
VALUES ('Реплика Проверкина', 'replication-proof@carrent.test')
RETURNING id, name, email, created_at;
```

```text
  id  |        name        |             email              |          created_at
------+--------------------+--------------------------------+-------------------------------
 5001 | Реплика Проверкина | replication-proof@carrent.test | 2026-09-14 07:48:24.951134+00
```

И обновление существующей строки:

```sql
UPDATE cars SET minute_fee = 99.99 WHERE id = 1 RETURNING id, model, minute_fee;
```

```text
 id |   model    | license_plate | minute_fee
----+------------+---------------+------------
  1 | Lada Vesta | A0001BC       |      99.99
```

## Чтение на Replica

Тот же `SELECT`, выполненный на втором узле, находит обе записи:

```text
[REPLICA]
  id  |        name        |             email              |          created_at
------+--------------------+--------------------------------+-------------------------------
 5001 | Реплика Проверкина | replication-proof@carrent.test | 2026-09-14 07:48:24.951134+00

[REPLICA]
 id |   model    | license_plate | minute_fee
----+------------+---------------+------------
  1 | Lada Vesta | A0001BC       |      99.99
```

Обратите внимание на `created_at`: время совпадает до микросекунды. Реплика не
выполняет `INSERT` заново — она побайтово применяет результат, уже зафиксированный
на Primary. Именно поэтому значения `now()`, `random()` и последовательностей на
обоих узлах одинаковы.

Отдельное подтверждение того, что узлы находятся на одной позиции журнала:

```text
[PRIMARY]  current_wal_lsn = 0/30426CC8
[REPLICA]  received = 0/30426CC8   replayed = 0/30426CC8
```

Массовая проверка: сразу после создания схемы на Primary реплика содержала
ровно те же данные.

| | Primary | Replica |
|---|---:|---:|
| `users` | 5 000 | 5 000 |
| `cars` | 1 000 | 1 000 |
| `rentals` | 200 000 | 200 000 |

# Часть 4. Replica доступна только для чтения

Все четыре попытки изменить данные на реплике отклонены:

```text
[REPLICA] INSERT INTO users ...
ERROR:  cannot execute INSERT in a read-only transaction

[REPLICA] UPDATE cars SET minute_fee = 1 WHERE id = 2;
ERROR:  cannot execute UPDATE in a read-only transaction

[REPLICA] DELETE FROM rentals WHERE id = 1;
ERROR:  cannot execute DELETE in a read-only transaction

[REPLICA] CREATE TABLE should_fail (id int);
ERROR:  cannot execute CREATE TABLE in a read-only transaction
```

Механизм виден в настройках сессии:

```text
 default_transaction_read_only    transaction_read_only
------------------------------    ---------------------
              off                          on
```

Параметр `default_transaction_read_only` выключен — то есть запрет не
настройка, которую администратор мог бы снять. `transaction_read_only`
принудительно равен `on`, потому что узел находится в состоянии восстановления.
Пока кластер остаётся standby, запись невозможна в принципе.

**Почему приложение не должно писать в Replica, даже если бы это было
технически возможно.** Реплика — не независимая база, а побайтовая копия
Primary, которая непрерывно перезаписывается потоком WAL. Собственная запись на
реплике не может ни попасть в этот поток, ни уехать обратно на Primary: у
физической репликации одно направление. Две базы немедленно разошлись бы в
данных, а любая операция, требующая изменения тех же страниц, привела бы к
конфликту и остановке репликации. Для записи существует ровно один узел —
Primary, и это гарантирует единый порядок транзакций.

# Часть 5. Чтение сервиса через Replica

## Как устроена маршрутизация

Сервис держит два независимых подключения и сам решает, куда отправить запрос
(`lab4/app/db.py`):

```python
PRIMARY = {"role": "PRIMARY", "host": "127.0.0.1", "port": "5432"}
REPLICA = {"role": "REPLICA", "host": "127.0.0.1", "port": "5433"}

def write(sql):    # любая модификация данных — только на Primary
    return _run(PRIMARY, sql)

def read(sql):     # чтение обслуживает Replica, разгружая Primary
    return _run(REPLICA, sql)
```

Эндпойнты (`lab4/app/carrent_api.py`):

| Эндпойнт | Операция | Узел |
|---|---|---|
| `POST /rentals` | `INSERT INTO rentals` | **Primary** |
| `GET /rentals?user_id=` | история аренд пользователя | **Replica** |
| `GET /rentals/statistics` | агрегат за 30 дней | **Replica** |
| `GET /cars/available` | каталог свободных машин | **Replica** |

## Фактический прогон

```text
Куда фактически подключается сервис
  PRIMARY  127.0.0.1:5432  -> узел сообщает о себе: PRIMARY
  REPLICA  127.0.0.1:5433  -> узел сообщает о себе: REPLICA

GET /rentals?user_id=42&limit=5
  -> REPLICA (127.0.0.1:5433)
   id   |    model    | minute_fee |          created_at
--------+-------------+------------+-------------------------------
  23117 | VW Polo     |      21.12 | 2026-09-13 14:41:46.301974+00
  ...

GET /rentals/statistics
  -> REPLICA (127.0.0.1:5433)
 rentals | users | avg_fee | total_fee
---------+-------+---------+------------
   66711 |  5000 |   15.03 | 1002516.77

POST /rentals  user_id=42 car_id=7
  -> PRIMARY (127.0.0.1:5432)
  создана аренда id=200001
```

Роль узла проверяется не по конфигурации, а запросом `pg_is_in_recovery()` к
каждому подключению — то есть сервис действительно разговаривает с разными
экземплярами.

## То же самое в реальном сервисе

CarRent написан на Django, и там маршрутизация описывается не в коде
эндпойнтов, а в настройках — Django сам выбирает подключение по типу операции
(`lab4/app/django_settings_snippet.py`):

```python
DATABASES = {
    "default": {...,  "HOST": "postgres_primary", "PORT": "5432"},
    "replica": {...,  "HOST": "postgres_replica", "PORT": "5432",
                "OPTIONS": {"options": "-c default_transaction_read_only=on"},
                "TEST": {"MIRROR": "default"}},
}
DATABASE_ROUTERS = ["RentSystem.routers.ReadWriteRouter"]


class ReadWriteRouter:
    def db_for_read(self, model, **hints):   return "replica"
    def db_for_write(self, model, **hints):  return "default"
    def allow_migrate(self, db, app_label, **hints):  return db == "default"
```

Три детали, без которых конфигурация была бы неполной:

- `default_transaction_read_only=on` на стороне клиента — страховка: ошибочный
  `UPDATE`, отправленный на реплику, упадёт сразу и явно;
- `allow_migrate` разрешает миграции только на Primary — на реплику схема
  приедет через WAL сама;
- `TEST: {"MIRROR": "default"}` не даёт Django пытаться создать тестовую базу
  на реплике.

Когда сразу после записи нужны гарантированно свежие данные, чтение
принудительно отправляется на Primary: `Rental.objects.using("default")`.

# Часть 6. Replication lag

## Отставание в покое

Когда поток записи мал, отставание практически отсутствует:

```text
 application_name |   state   | bytes_behind |    write_lag    |    flush_lag    |   replay_lag
------------------+-----------+--------------+-----------------+-----------------+-----------------
 walreceiver      | streaming |            0 | 00:00:00.000383 | 00:00:00.000681 | 00:00:00.000728
```

Ноль байт разницы между `sent_lsn` и `replay_lsn` и доли миллисекунды на
запись, сброс и применение. Именно поэтому поймать лаг «вручную» не удаётся —
см. опыт 1.

## Опыт 1. Гонка «записал и сразу прочитал»

20 итераций: `INSERT` на Primary, затем чтение с Replica в цикле до появления
записи.

```text
мин 50.1 мс, медиана 53.9 мс, макс 59.3 мс
случаев, когда Replica ещё не содержала запись: 0
```

Поймать отставание таким способом **не удалось**, и это честный результат, а не
неудача эксперимента: репликация на локальной машине укладывается в доли
миллисекунды, тогда как каждое измерение включает запуск `psql` и установку
нового TCP-соединения — десятки миллисекунд. Инструмент измерения оказался
грубее измеряемой величины.

## Опыт 2. Воспроизводимое отставание

Чтобы увидеть момент рассинхронизации гарантированно, применение WAL на реплике
приостанавливается штатной функцией:

```sql
-- на Replica
SELECT pg_wal_replay_pause();
```

Реплика продолжает **принимать** WAL, но перестаёт его **применять**. Дальше —
запись на Primary и чтение обоих узлов:

```text
Замораживаем применение WAL на Replica
  pg_wal_replay_pause() выполнен, состояние: paused

Пишем на Primary, пока реплика заморожена:
Primary уже видит запись:
   count = 1
Replica ещё НЕ видит:
   count = 0

Отставание в этот момент (в байтах WAL), по данным Primary:
 application_name | bytes_behind |   replay_lag
------------------+--------------+-----------------
 walreceiver      |          288 | 00:00:00.000576

Возобновляем применение WAL:
Replica догнала:
   count = 1
```

Вот он, искомый момент: Primary содержит новое значение, Replica ещё нет.

## Опыт 3. Естественное отставание под нагрузкой

Ситуация, близкая к рабочей: массовая вставка 400 000 строк одним запросом.

```text
Заливаем 400000 строк одним INSERT и параллельно следим за Replica
  LSN на Primary до записи: 0/30428540
  запись заняла 4472 мс, замеров во время записи: 56
  пиковое отставание: 13507616 байт WAL (12.9 МБ), replay_lag до 305.287 мс
  через секунду после записи отставание: 0 байт
  строк в rentals — Primary: 620000, Replica: 620000
```

Здесь никаких искусственных пауз: реплика отстала на **12.9 МБ WAL** и до
**305 мс** просто потому, что Primary порождал журнал быстрее, чем реплика
успевала его применять. Через секунду после завершения записи отставание
вернулось к нулю.

Важная деталь методики: замерять отставание **после** завершения `INSERT`
бесполезно — за 4.5 секунды записи реплика успевает догнать, и результат
оказывается нулевым. Поэтому запись выполняется в отдельном потоке, а
отставание снимается параллельно, пока транзакция ещё идёт (56 замеров).

## Вывод

Репликация не означает мгновенную синхронизацию. Между фиксацией транзакции на
Primary и её применением на Replica всегда существует задержка. В покое она
исчезающе мала (сотые доли миллисекунды), но растёт вместе с потоком записи и
при всплеске нагрузки достигает сотен миллисекунд.

Практическое следствие для сервиса: сценарий «пользователь оформил аренду и
сразу открыл список своих аренд» может показать список **без** только что
созданной записи, если чтение ушло на реплику. Там, где это недопустимо, чтение
после записи направляют на Primary явно (`using("default")` в Django).

Асинхронность здесь — сознательный выбор: `sync_state = async` означает, что
Primary подтверждает транзакцию клиенту, не дожидаясь реплики. Это быстро, но
допускает лаг. Синхронная репликация (`synchronous_commit = on` плюс
`synchronous_standby_names`) убрала бы лаг для чтения, но заставила бы каждую
запись ждать подтверждения реплики — и остановила бы запись совсем, если
реплика недоступна.

# Контрольные вопросы

**1. Чем Primary отличается от Replica?**
Primary — единственный узел, принимающий запись; он порождает поток WAL.
Replica постоянно находится в режиме восстановления (`pg_is_in_recovery() = t`)
и только применяет этот поток, обслуживая запросы на чтение. Технически это
проявляется в том, что на реплике `transaction_read_only = on` принудительно,
и любая попытка записи отклоняется.

**2. Почему запись выполняем на Primary?**
Потому что у физической репликации одно направление: WAL идёт от Primary к
Replica и никогда обратно. Запись на реплике не смогла бы попасть на Primary, и
узлы разошлись бы в данных. Единственный пишущий узел задаёт единый порядок
транзакций и гарантирует, что у всех копий одна и та же история изменений.

**3. Как изменение из Primary попадает на Replica?**
Транзакция на Primary сначала записывается в WAL. Процесс `walsender`
отправляет эти записи по TCP процессу `walreceiver` на реплике; тот сохраняет
их в свой WAL, а startup process применяет их к файлам данных. В опыте это
видно по совпадающим LSN: `sent_lsn = 0/752CED8` на Primary и
`written_lsn = flushed_lsn = 0/752CED8` на Replica.

**4. Что такое WAL в контексте репликации?**
Write-Ahead Log — журнал предзаписи: любое изменение сначала попадает в него, и
только потом в файлы данных. Изначально он нужен для восстановления после сбоя,
но для репликации он же служит потоком изменений: реплика получает не SQL-текст
запросов, а готовые физические записи «на такой-то странице изменить такие-то
байты». Поэтому реплика не выполняет `INSERT` заново, и значения `now()`,
`random()` и последовательностей на обоих узлах совпадают.

**5. Что такое replication lag?**
Задержка между фиксацией транзакции на Primary и её применением на Replica.
Измеряется в байтах WAL (`pg_wal_lsn_diff(sent_lsn, replay_lsn)`) и во времени
(`write_lag`, `flush_lag`, `replay_lag`). В покое на стенде — 0 байт и
сотые доли миллисекунды; под нагрузкой в 400 000 строк — до 62 507 016 байт и
493 мс.

**6. Почему следующий SELECT после INSERT может увидеть старые данные, если
отправить его на Replica?**
Потому что подтверждение клиенту приходит от Primary, не дожидаясь реплики:
`sync_state = async`. В промежутке между фиксацией на Primary и применением на
Replica реплика физически содержит старое состояние. Этот момент воспроизведён
в части 6: при замороженном применении WAL Primary показывал `count = 1`, а
Replica — `count = 0`.

**7. Что именно масштабируется при Read Scaling?**
Способность системы обслуживать **больше** чтений, а не скорость одного
запроса. Отдельный `SELECT` на реплике выполняется примерно столько же, сколько
на Primary — то же железо, те же индексы, тот же план. Выигрыш в том, что
читающие запросы распределяются между узлами: Primary разгружается от
аналитики и списков, оставляя ресурсы для записи, а добавление ещё одной
реплики почти линейно увеличивает суммарный поток чтений. Пропускная
способность записи при этом не растёт вовсе — пишущий узел по-прежнему один.

**8. Почему наличие Replica не отменяет необходимость индексов и оптимизации SQL?**
Реплика — точная копия Primary вместе со всеми его недостатками. Запрос,
который делает `Seq Scan` по 10 миллионам строк, будет делать ровно тот же
`Seq Scan` и на реплике, только на другом сервере. Репликация меняет, **где**
выполняется запрос, а индексы и оптимизация меняют, **сколько работы** он
выполняет. Более того, неоптимизированные запросы на реплике вредят вдвойне:
долгие транзакции на standby конфликтуют с применением WAL, из-за чего растёт
lag, а при `max_standby_streaming_delay` такие запросы принудительно
отменяются.

**9. Расскажите про CAP-теорему.**
CAP утверждает, что распределённая система не может одновременно обеспечивать
все три свойства:

- **Consistency** — любое чтение возвращает последнюю записанную версию данных;
- **Availability** — каждый работающий узел отвечает на запрос;
- **Partition tolerance** — система продолжает работать при потере связи между
  узлами.

Сетевые разделения в реальности неизбежны, поэтому `P` не выбирают — с ним
приходится жить, а выбор происходит между `C` и `A` в момент разделения.

Наш стенд — наглядная иллюстрация. Асинхронная репликация с чтением на реплике
выбирает **AP**: реплика продолжает отвечать, даже потеряв связь с Primary, но
отдаёт возможно устаревшие данные — то самое нарушение строгой согласованности,
которое мы измерили как replication lag. Если переключить систему в синхронный
режим (`synchronous_standby_names`), она сместится в сторону **CP**: чтение с
реплики перестанет отдавать устаревшее, но при недоступности реплики Primary
остановит запись, то есть пожертвует доступностью.

Стоит добавить, что CAP описывает поведение именно в момент разделения сети, а
не в нормальном режиме, и оперирует крайними определениями (строгая
линеаризуемость против полной доступности). На практике системы выбирают
промежуточные уровни согласованности — например, read-your-writes, который в
нашем сервисе реализуется просто: чтение сразу после записи направляется на
Primary, а всё остальное уходит на Replica.
