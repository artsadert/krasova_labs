# Часть 1. RANGE PARTITIONING по дате

Создана таблица `events` с `PARTITION BY RANGE (created_at)` и тремя суточными
партициями. Загружено 3 000 030 строк (позже к ним добавились две пробные
записи из вопросов ниже), распределение равномерное:

```text
  partition_name   |  count
-------------------+---------
 events_2026_09_09 | 1000010
 events_2026_09_10 | 1000010
 events_2026_09_11 | 1000010
```

**1. В какую партицию попадёт запись с `created_at = '2026-09-10 12:00:00'`?**

В `events_2026_09_10`. Проверено вставкой:

```text
    id    |  partition_name   |     created_at
----------+-------------------+---------------------
 99000001 | events_2026_09_10 | 2026-09-10 12:00:00
 99000002 | events_2026_09_11 | 2026-09-11 00:00:00
```

**2. В какую партицию попадёт запись с `created_at = '2026-09-11 00:00:00'`?**

В `events_2026_09_11`, а не в `events_2026_09_10`. Полночь 11 сентября — это
нижняя граница третьей партиции, и нижняя граница включается.

**3. Что произойдёт, если вставить запись за 2026-09-12?**

Вставка завершится ошибкой — подходящей партиции не существует:

```text
ERROR:  no partition of relation "events" found for row
DETAIL:  Partition key of the failing row contains (created_at) = (2026-09-12 10:00:00).
```

Это и есть причина, по которой партиции необходимо создавать заранее и
автоматически: без свободной партиции приложение перестаёт писать данные.
Именно эта ситуация отрабатывается в частях 10 и 11.

**4. Почему граница `TO ('2026-09-11')` не включает эту дату?**

В PostgreSQL границы RANGE-партиции полуоткрытые: `FROM` включается,
`TO` исключается, то есть `[FROM, TO)`. Фактические границы, как их хранит сама
СУБД:

```text
 events_2026_09_10 | FOR VALUES FROM ('2026-09-10 00:00:00') TO ('2026-09-11 00:00:00')
 events_2026_09_11 | FOR VALUES FROM ('2026-09-11 00:00:00') TO ('2026-09-12 00:00:00')
```

Так сделано, чтобы соседние партиции стыковались без зазоров и без пересечений:
верхняя граница одной буквально равна нижней границе следующей. Если бы `TO`
включалась, полночь 11 сентября принадлежала бы сразу двум партициям, и
однозначно определить место строки было бы невозможно.

# Часть 2. Partition pruning

**Запрос по диапазону дат:**

```sql
SELECT COUNT(*) FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11';
```

```text
Finalize Aggregate
  ->  Gather  (Workers Launched: 2)
        ->  Partial Aggregate
              ->  Parallel Seq Scan on events_2026_09_10 events
                    Filter: ((created_at >= '2026-09-10 00:00:00') AND (created_at < '2026-09-11 00:00:00'))
                    Buffers: shared hit=5575 read=3890
Execution Time: 79.892 ms
```

- **Сколько партиций проверено:** одна.
- **Какая нужна:** `events_2026_09_10`.
- **Удалось ли исключить остальные:** да, обе.
- **Где в плане видно pruning:** по тому, чего в плане *нет*. Отсутствует узел
  `Append`, который объединял бы партиции, и не упомянуты
  `events_2026_09_09` / `events_2026_09_11`. Планировщик отбросил их ещё на
  этапе планирования, поэтому в плане они не появляются вовсе. Прочитано
  9 465 буферов вместо 28 395.

**Запрос по `event_type`:**

```sql
SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

```text
->  Parallel Append
      ->  Parallel Seq Scan on events_2026_09_09 events_1   Rows Removed by Filter: 266667
      ->  Parallel Seq Scan on events_2026_09_10 events_2   Rows Removed by Filter: 800001
      ->  Parallel Seq Scan on events_2026_09_11 events_3   Rows Removed by Filter: 400000
Buffers: shared hit=15905 read=12490
Execution Time: 133.209 ms
```

**Почему второй запрос обращается ко всем партициям?**

Таблица разделена по `created_at`, а условие поставлено на `event_type`.
Значение `event_type = 'click'` может лежать в любой партиции — по ключу
партиционирования запрос не ограничен ничем, поэтому исключить нельзя ни одну.
В плане появился `Parallel Append`, объединяющий все три партиции, и прочитано
28 395 буферов против 9 465 у первого запроса.

Отсюда главный принцип: **pruning работает только по ключу партиционирования**.

# Часть 3. RANGE PARTITIONING по числовому значению

Таблица `products` разделена по `price` на `cheap` `[0,100)`,
`medium` `[100,1000)` и `expensive` `[1000, MAXVALUE)`.

```text
   partition_name   | count |   min   |   max
--------------------+-------+---------+----------
 products_cheap     |     2 |   25.00 |    99.99
 products_medium    |     3 |  100.00 |   999.99
 products_expensive |     2 | 1000.00 | 25000.00
```

Товар за 99.99 попал в `cheap`, а ровно за 100.00 — уже в `medium`: то же
правило полуоткрытого интервала, что и с датами.

**Какие партиции PostgreSQL должен просмотреть для `price >= 100 AND price < 500` и почему?**

Только `products_medium`. Запрошенный диапазон `[100, 500)` целиком лежит внутри
границ этой партиции `[100, 1000)`. `cheap` заканчивается на 100, `expensive`
начинается с 1000 — ни одна из них не может содержать подходящих строк.
Подтверждается планом:

```text
Seq Scan on products_medium products
  Filter: ((price >= '100'::numeric) AND (price < '500'::numeric))
  Rows Removed by Filter: 1
Execution Time: 0.026 ms
```

Обратите внимание на `Rows Removed by Filter: 1`: pruning отсёк лишние
*партиции*, но внутри оставшейся условие всё равно проверяется для каждой
строки — партиционирование не заменяет фильтрацию.

# Часть 4. LIST PARTITIONING

Таблица `customers` разделена по `customer_type`, загружено по 10 000 клиентов
каждого типа.

```sql
SELECT * FROM customers WHERE customer_type = 'B2B';
```

```text
Seq Scan on customers_b2b customers  (actual rows=10000.00)
  Filter: ((customer_type)::text = 'B2B'::text)
  Buffers: shared hit=71
Execution Time: 2.341 ms
```

- **Какая партиция используется:** только `customers_b2b`.
- **Почему PostgreSQL не обращается к другим:** значение `'B2B'` явно и
  однозначно закреплено за одной партицией списком `FOR VALUES IN ('B2B')`.
  В `customers_b2c` и `customers_enterprise` строк с таким значением не может
  быть по определению партиции, и планировщик отбрасывает их сразу.
- **Чем сценарий отличается от RANGE:** в RANGE партиция задаётся интервалом, и
  запрос может задеть несколько партиций сразу (диапазон дат за квартал
  затронет три месячные партиции). В LIST партиция задаётся перечислением
  конкретных значений, поэтому равенство всегда указывает ровно на одну
  партицию. LIST подходит для ограниченного и стабильного набора категорий,
  RANGE — для непрерывных величин, которые постоянно растут.

# Часть 5. LIST PARTITIONING: неизвестное значение

Попытка вставить клиента с типом `VIP`, для которого партиции нет:

```text
ERROR:  no partition of relation "customers" found for row
DETAIL:  Partition key of the failing row contains (customer_type) = (VIP).
```

После создания `customers_default` та же вставка проходит, и строка попадает
в DEFAULT-партицию:

```text
 id  |   name    | customer_type |  partition_name
-----+-----------+---------------+--------------------
 100 | Test User | VIP           | customers_default
```

**1. Зачем нужна DEFAULT partition?**
Она принимает строки, не подошедшие ни под одну из объявленных партиций.
Без неё любое новое значение ключа приводит к ошибке вставки, то есть к отказу
приложения.

**2. Чем она полезна?**
Это страховка от потери данных. Появление нового типа клиента не роняет
запись: строка сохраняется, приложение продолжает работать, а инженеры могут
разобраться позже. Для RANGE-партиционирования по дате DEFAULT играет ту же
роль, что и health check из части 11 — не даёт INSERT упасть, если ночная job
не отработала.

**3. Какие проблемы возникают, если постоянно складывать новые значения в DEFAULT?**

Три реальные проблемы, первая из которых воспроизведена на практике.

*Невозможно потом выделить нормальную партицию.* Попытка создать партицию для
`VIP` уже после того, как строка с этим значением попала в DEFAULT:

```text
ERROR:  updated partition constraint for default partition "customers_default"
        would be violated by some row
```

PostgreSQL обязан проверить, что ни одна строка из DEFAULT не должна была бы
принадлежать новой партиции. Пока такие строки там лежат, создать партицию
нельзя — сначала их нужно оттуда убрать.

*DEFAULT растёт неограниченно и убивает pruning.* Планировщик не знает, какие
значения лежат в DEFAULT, поэтому исключить её может далеко не всегда. Она
превращается в ту самую большую нераздёленную таблицу, ради избавления от
которой и затевалось партиционирование.

*Проблема остаётся незамеченной.* Вставка не падает, ошибок в логах нет, и
данные тихо копятся не там, где должны. DEFAULT стоит использовать как
аварийный буфер с обязательным мониторингом её размера, а не как штатное место
хранения.

# Часть 6. HASH PARTITIONING

Таблица `user_events` разделена по `HASH (user_id)` на 4 партиции, загружен
1 000 000 строк.

**1. Насколько равномерно распределились данные?**

```text
 partition_name | count  |  pct
----------------+--------+-------
 user_events_0  | 249361 | 24.94
 user_events_1  | 250392 | 25.04
 user_events_2  | 250071 | 25.01
 user_events_3  | 250176 | 25.02
```

Практически идеально: отклонение от ровных 25% не превышает 0.06 процентного
пункта. Это и есть смысл хеширования — оно не зависит от того, как значения
`user_id` распределены в реальности.

**2. Почему HASH может быть полезен?**
Когда данные нужно просто разложить по нескольким физическим частям, а
естественного диапазона или набора категорий нет. Это даёт меньший размер
каждой партиции и её индексов, распараллеливание сканирования и снижение
конкуренции при массовых вставках. Запрос по конкретному `user_id` при этом
попадает ровно в одну партицию — pruning работает:

```text
Parallel Seq Scan on user_events_1 user_events
  Filter: (user_id = 555)
```

**3. Чем HASH отличается от RANGE?**
В RANGE партиция определяется диапазоном значений, и физическое расположение
данных осмысленно: «здесь июнь, здесь июль». В HASH партиция определяется
остатком от деления хеша, и связи между содержимым партиции и смыслом данных
нет. Как следствие, HASH поддерживает pruning только для условий на равенство:
запрос по диапазону дат читает все четыре партиции (135.378 мс) против одной
при поиске по `user_id` (19.365 мс).

**4. Почему HASH плохо подходит для сценария «удалить данные старше 3 лет»?**
При RANGE по дате старые данные лежат в отдельных партициях, и удаление — это
мгновенный `DROP TABLE`/`DETACH PARTITION` без чтения строк. При HASH записи
всех возрастов равномерно перемешаны внутри каждой партиции, целиком удалить
нельзя ни одну. Остаётся обычный `DELETE ... WHERE created_at < ...`, который
читает все партиции, генерирует WAL, оставляет раздутие и требует `VACUUM` —
то есть ровно то, от чего партиционирование должно было избавить.

# Часть 7. Выбор стратегии партиционирования

| Сценарий | Стратегия | Обоснование |
|---|---|---|
| **A.** Миллионы событий в день, через 3 года быстро удалять старше 3 лет | **RANGE по дате** (по месяцам или дням) | Только RANGE по времени превращает удаление старых данных в мгновенный `DETACH`/`DROP` целой партиции вместо `DELETE` миллиардов строк. Плюс запросы за период получают pruning. |
| **B.** Пользователи B2C / B2B / Enterprise, фильтрация по этому признаку | **LIST по `customer_type`** | Набор значений мал, фиксирован и осмыслен, а основной запрос — равенство по этой колонке, то есть попадает ровно в одну партицию (часть 4). |
| **C.** Равномерно распределить данные по `user_id` | **HASH по `user_id`** | Естественных диапазонов и категорий у `user_id` нет, а хеш даёт равномерность независимо от распределения (часть 6: отклонение не более 0.06 п.п.). |
| **D.** Заказы, аналитика по `created_at BETWEEN ...` | **RANGE по `created_at`** | Ключ партиционирования совпадает с колонкой, по которой идёт фильтрация, поэтому pruning отсекает всё лишнее. Дополнительно появляется дешёвая архивация старых периодов. |
| **E.** Платежи по странам EE / LV / LT / FI / SE | **LIST по коду страны** | Список стран ограничен и меняется редко; запросы обычно идут по конкретной стране. Стоит сразу добавить DEFAULT-партицию на случай новой страны, помня об ограничениях из части 5. |

Для сценариев A и D при очень больших объёмах разумно и **двухуровневое
партиционирование**: RANGE по месяцу, а внутри — HASH по `user_id`.

# Часть 8. Партиционирование и индексы

```sql
CREATE INDEX idx_events_user_id ON events (user_id);
```

**3. На каком уровне существует индекс?**

Команда, выполненная над родительской таблицей, создала четыре объекта:

```text
          index_name           | is_partition_index |     on_table
-------------------------------+--------------------+-------------------
 events_2026_09_09_user_id_idx | t                  | events_2026_09_09
 events_2026_09_10_user_id_idx | t                  | events_2026_09_10
 events_2026_09_11_user_id_idx | t                  | events_2026_09_11
 idx_events_user_id            | f                  | events
```

Индекс на родителе — «виртуальный»: он не хранит данных и служит шаблоном.
Реальные B-деревья существуют отдельно в каждой партиции. Важное следствие:
при создании новой партиции PostgreSQL автоматически создаёт в ней все индексы
родителя — job из части 10 не обязана делать это сама.

**1. Какие партиции отфильтрованы через pruning, и 2. используется ли индекс?**

```sql
SELECT * FROM events
WHERE created_at >= '2026-09-10' AND created_at < '2026-09-11' AND user_id = 12345;
```

```text
Bitmap Heap Scan on events_2026_09_10 events
  Recheck Cond: (user_id = 12345)
  Filter: ((created_at >= '2026-09-10 00:00:00') AND (created_at < '2026-09-11 00:00:00'))
  Heap Blocks: exact=18
  Buffers: shared hit=24
  ->  Bitmap Index Scan on events_2026_09_10_user_id_idx
        Index Cond: (user_id = 12345)
Execution Time: 0.247 ms
```

Отфильтрованы `events_2026_09_09` и `events_2026_09_11` — в плане их нет.
Индекс используется, причём именно индекс нужной партиции
(`events_2026_09_10_user_id_idx`), а не родительский. Прочитано 24 буфера.

**4. Почему комбинация partitioning + index эффективнее, чем один механизм?**

Они устраняют разные потери. Партиционирование отсекает **лишние партиции** до
того, как хоть одна страница прочитана. Индекс внутри оставшейся партиции
отсекает **лишние строки**. Сравнение на тех же данных:

| Что применяется | План | Буферы | Время |
|---|---|---:|---:|
| Только pruning (часть 2, `COUNT` за день) | `Parallel Seq Scan` по одной партиции | 9 465 | 79.892 ms |
| Только индекс (`user_id = 12345` без даты) | `Append` по трём партициям, индекс в каждой | 48 | 0.320 ms |
| **Pruning + индекс** | `Bitmap Index Scan` в одной партиции | **24** | **0.247 ms** |

Вдобавок индексы становятся меньше: вместо одного дерева на 3 000 000 строк —
три по 16 MB на партицию. Дерево меньшей высоты быстрее обходится и с большей
вероятностью целиком лежит в кэше.

# Часть 9. Когда партиционирование не помогает

```sql
SELECT COUNT(*) FROM events WHERE event_type = 'click';
```

| Вариант | План | Буферы | Время |
|---|---|---:|---:|
| До индекса | `Parallel Append` по 3 партициям, `Parallel Seq Scan` | 28 395 | 127.319 ms |
| После `idx_events_event_type` | `Parallel Append` по 3 партициям, `Bitmap Index Scan` | 28 950 | **124.753 ms** |
| Индекс + условие по дате | одна партиция, `Bitmap Index Scan` | 9 676 | **37.651 ms** |

**Почему partitioning сам по себе не решил проблему этого запроса?**

Потому что условие поставлено не на ключ партиционирования. Таблица разделена
по `created_at`, а фильтр идёт по `event_type`, значения которого равномерно
размазаны по всем партициям. Исключить нечего — читаются все три.

Индекс по `event_type` тоже почти не помог: 124.753 мс против 127.319 мс.
Причина уже знакома по лабораторной №2 — `'click'` составляет пятую часть
таблицы (600 030 строк из 3 000 032). Индекс полезен, когда позволяет **не
читать** большую часть страниц, а здесь подходящие строки есть практически на
каждой странице.

Работает только комбинация: добавление условия по дате включает pruning, и
время падает до 37.651 мс.

**Вывод: партиционирование отвечает на одну проблему, а индекс — на другую.**

Партиционирование отвечает на вопрос «какие *куски таблицы* можно вообще не
трогать» и работает исключительно по ключу партиционирования; попутно оно
решает эксплуатационные задачи — удаление старых данных, размер индексов,
обслуживание по частям. Индекс отвечает на вопрос «какие *строки* внутри куска
нужны» и работает по любой проиндексированной колонке, но только при высокой
селективности. Ни один из механизмов не заменяет другой, и оба бессильны, если
запрос по своей природе обязан обработать значительную часть данных.

| Событие | Предыдущее состояние | Действие |
|---|---|---|
| CRITICAL | OK | отправить alert |
| CRITICAL | CRITICAL | промолчать (или повторить, если задан `--repeat-after`) |
| OK | CRITICAL | отправить recovery |
| OK | OK | промолчать |

Опция `--repeat-after N` позволяет напоминать о незакрытой проблеме не чаще
раза в N секунд — на случай, если инцидент не разобрали за смену.

# Часть 12. Партиционирование собственной базы данных

## Шаги 1-4. Выбор таблицы, ключа и стратегии

**Таблица:** `rentals` сервиса CarRent — факт аренды автомобиля.
**Ключ:** `created_at`. **Стратегия:** `RANGE`, партиция на календарный месяц.

**Почему именно эта таблица?** Это единственная по-настоящему растущая таблица
сервиса: `cars`, `users`, `car_categories`, `parking_areas` — справочники,
ограниченные размером автопарка и клиентской базы. При автопарке в 50 000
машин и 3-5 поездках на машину в день `rentals` прибавляет около 200 000 строк
в сутки, порядка 70 миллионов в год, и потолка у неё нет. В лабораторной №2
именно на этой таблице запрос по диапазону дат оказался узким местом: с
индексом он всё равно рос с 2.4 мс на 100 тысячах до 111.4 мс на 5 миллионах.

**Почему именно этот ключ?** Аренда неизменно привязана ко времени, а все
тяжёлые сценарии сервиса — отчёты и статистика — фильтруют именно по периоду.
Кроме того, у данных есть естественный жизненный цикл: аренды старше
нескольких лет нужны только для архива, и RANGE по дате превращает их удаление
в `DETACH PARTITION`.

**Почему именно эта стратегия?** LIST не подходит — у времени нет конечного
набора значений. HASH дал бы равномерность, но лишил бы главного: возможности
отсекать периоды и мгновенно удалять старое (часть 6, вопрос 4). Месяц как
размер партиции выбран из расчёта около 500 000 строк и ~45 MB на партицию:
сутки дали бы 700+ партиций в год и раздутый каталог, год — партиции, слишком
крупные для pruning.

**Какие запросы должны получить пользу от pruning?** Отчёты и статистика за
период, выгрузка аренд за интервал дат, а также любые ночные пересчёты по
месяцу. Запросы по `id` и `user_id` пользы не получат — это осознанный размен,
измеренный ниже.

Отдельное следствие партиционирования: первичный ключ обязан включать ключ
партиционирования, поэтому `PRIMARY KEY (id)` превратился в
`PRIMARY KEY (id, created_at)`. Это надо учитывать в ORM и во внешних ключах.

## Шаг 6. Проверка реальных запросов API

| Запрос API | SQL-условие | Партиций в плане | Pruning | Время |
|---|---|---:|---|---:|
| `GET /rentals?from=2026-08-01&to=2026-09-01` | `created_at` BETWEEN | 1 из 4 | **да** | 54.391 ms |
| `GET /rentals/{id}` | `id = 1234567` | 4 из 4 | нет | 0.202 ms |
| `GET /rentals/{id}` + месяц | `id` + `created_at` | 1 из 4 | **да** | 0.086 ms |
| `GET /rentals/statistics?month=2026-08` | агрегат за месяц | 1 из 4 | **да** | 79.091 ms |
| История пользователя | `user_id = 4242` | 4 из 4 | нет | 0.283 ms |
| История пользователя + месяц | `user_id` + `created_at` | 1 из 4 | **да** | 0.211 ms |

Pruning получают все запросы, где указан период, — то есть именно те, ради
которых партиционирование и вводилось. Запросы по `id` и `user_id` вынуждены
заглядывать во все четыре партиции (`Append` с `Index Scan` в каждой), но
остаются быстрыми, потому что в каждой партиции работает индекс: цена
отсутствия pruning здесь — доли миллисекунды.

Для сравнения та же статистика была выполнена на непартиционированной копии
тех же 2 000 000 строк с индексом по `created_at`:

| | План | Время |
|---|---|---:|
| Партиционированная `rentals` | `Aggregate → Parallel Seq Scan` по одной партиции | **79.091 ms** |
| Обычная `rentals_plain` | `Aggregate → Gather → Index Scan` по всей таблице | 156.136 ms |

Выигрыш почти вдвое, причём партиционированный вариант обошёлся вообще без
индекса: прочитать одну партицию целиком дешевле, чем идти через индекс по
таблице вчетверо большего размера.

# Alert-система в Docker

Вся эксплуатационная часть (части 10-11) упакована в отдельный сервис
`partition_alerts`, который поднимается вместе с базой:

```bash
docker compose --env-file ./.env up -d partition_alerts
docker compose logs -f partition_alerts
```

## Из чего состоит

`jobs/Dockerfile` собирает образ на `python:3.13-slim`. Единственная
устанавливаемая зависимость — `postgresql-client`: код ходит в базу через
`psql`, внешних Python-пакетов система не требует вовсе.

Внутри контейнера вместо cron работает `jobs/scheduler.py`: он периодически
запускает `CreatePartitionsJob` и чаще — `PartitionHealthCheck`, а логи пишет
в stdout, как и положено контейнеру. Наблюдаемые таблицы задаются одной
переменной:

```yaml
WATCH: "krasova_lab3:events:day:3,carrent_lab3:rentals:month:2"
JOB_INTERVAL: 3600      # как часто создавать будущие партиции
CHECK_INTERVAL: 300     # как часто проверять горизонт
```

Формат — `схема:таблица:гранулярность:горизонт`, поэтому одна и та же система
следит и за суточными партициями `events`, и за помесячными `rentals`,
и состояние алертов хранит для каждой таблицы отдельно.

## Три решения, которые пришлось принять

**Подключение к базе.** Локально job ходит в базу через
`docker exec database_postgres psql`, но изнутри контейнера такой команды нет.
Поэтому `db.py` выбирает режим сам: если задан `PGHOST` — подключается по сети
(`psql -h postgres`), иначе использует `docker exec`. В compose выставлено
`PGHOST: postgres`, и тот же код работает в обоих сценариях без правок.

**Секреты.** Токен и chat_id лежат только в `.env`, который передаётся
контейнеру через `env_file`. В `docker-compose.yaml`, в `Dockerfile` и в самом
образе их нет; в `crontab.example` они тоже больше не прописываются, потому что
crontab читается любым процессом пользователя, а аргументы командной строки
видны в `ps`.

**Состояние алертов.** Файл состояния вынесен в именованный том
`partition_state`, смонтированный в `/state`. Без этого после каждого рестарта
контейнера система считала бы, что видит проблему впервые, и повторно слала бы
alert об уже известном инциденте — ровно то, от чего защищает часть 11.4.

Контейнер работает под непривилегированным пользователем `partitions` (uid
10001). Здесь есть неочевидная тонкость, на которой сборка сначала и сломалась:
каталог `/state` нужно создать и передать пользователю **до** инструкции
`VOLUME`. Всё, что делается с каталогом после объявления тома, Docker
отбрасывает, поэтому том остался принадлежать root, и процесс падал с
`PermissionError` при попытке сохранить состояние.

Дополнительно у сервиса есть `HEALTHCHECK`, который проверяет, что база
действительно доступна (`SELECT 1`), — иначе «живой» контейнер мог бы часами
молча не выполнять проверок.

# pg_cron: создание партиций внутри СУБД

## Зачем понадобилось

Внешняя `CreatePartitionsJob` из части 10 создаёт партиции по расписанию
контейнера, и между двумя её запусками система знает о проблеме, но не чинит
её: health check обнаруживал пропавшую партицию каждые 30 секунд и слал alert,
а исправление приходило только со следующим запуском job — то есть с задержкой
до `JOB_INTERVAL`. Это ровно тот разрыв, из-за которого удалённая вручную
партиция «не возвращалась»: она возвращалась, но через десять минут.

`pg_cron` убирает разрыв: расписание живёт внутри СУБД, выполняется раз в
минуту и не зависит от того, жив ли контейнер приложения.

## Сборка образа

`Dockerfile` проекта теперь ставит оба расширения:

```dockerfile
FROM postgres:18
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      postgresql-18-postgis \
      postgresql-18-cron \
 && rm -rf /var/lib/apt/lists/*
COPY docker/init/ /docker-entrypoint-initdb.d/
```

`pg_cron` нельзя включить на лету: он загружается через
`shared_preload_libraries`, то есть только при старте сервера. Параметры
задаются в `docker-compose.yaml`:

```yaml
command:
  - postgres
  - -c
  - shared_preload_libraries=pg_cron
  - -c
  - cron.database_name=${DB_DATABASE:-postgres}
```

`cron.database_name` указывает, в какой базе кластера живёт расширение и его
расписание — `pg_cron` работает в одной базе, а не во всём кластере сразу.
Проверка после старта:

```text
LOG:  pg_cron scheduler started

  Name   | Version |   Schema   |         Description
---------+---------+------------+------------------------------
 pg_cron | 1.6     | pg_catalog | Job scheduler for PostgreSQL
```

## Где это выполняется

`pg_cron` — не отдельный процесс и не системный cron. Постмастер запускает
**фоновый рабочий процесс** (background worker), который и ведёт расписание;
для каждого срабатывания он запускает ещё один фоновый процесс, выполняющий
SQL в указанной базе. Поэтому расписание:

- хранится в обычной таблице `cron.job` и попадает в `pg_dump` вместе с базой;
- переживает перезапуск и пересоздание контейнера;
- ведёт историю в `cron.job_run_details`.

## Что именно запланировано

Логика вынесена в схему `partition_ops` (`lab3/sql/03_pg_cron.sql`): функции
считают требуемый горизонт, находят недостающие партиции и создают их,
записывая результат в `partition_ops.run_log`. Расписание:

```sql
SELECT cron.schedule('partitions-events', '* * * * *',
       $$ SELECT partition_ops.ensure_partitions('krasova_lab3','events','day',3) $$);
SELECT cron.schedule('partitions-rentals', '* * * * *',
       $$ SELECT partition_ops.ensure_partitions('carrent_lab3','rentals','month',2) $$);
```

```text
 jobid |      jobname       | schedule  | active | database
-------+--------------------+-----------+--------+----------
     1 | partitions-events  | * * * * * | t      | postgres
     2 | partitions-rentals | * * * * * | t      | postgres
```

## Как уведомления попадают наружу

У PostgreSQL нет HTTP-клиента, поэтому задание `pg_cron` физически не может
постучаться в Telegram. Используется паттерн **outbox**: задание складывает
сообщение в таблицу `partition_ops.alert_outbox`, а `jobs/alert_relay.py`
забирает неотправленные строки, доставляет их и проставляет `sent_at`. Если
канал недоступен, строка остаётся в очереди и будет повторена — сообщение не
теряется.

```
pg_cron (внутри СУБД)                 контейнер partition_alerts
  ensure_partitions()
    ├─ CREATE TABLE ... PARTITION OF
    ├─ run_log        (журнал действий)
    └─ alert_outbox ──────────────────▶ alert_relay.py ──HTTPS──▶ Telegram
                                        partition_health_check.py ──▶ Telegram
```

За контейнером остались две функции: контроль горизонта (чтобы поймать отказ
самого `pg_cron`) и доставка уведомлений. Создание партиций он больше не
дублирует — это включается переменной `USE_PG_CRON: "true"`.

# Контрольные вопросы

**1. Что такое partitioning?**
Разделение одной логической таблицы на несколько физических частей (партиций)
по значению ключа партиционирования. Для приложения таблица остаётся одной:
запросы пишутся к родителю, а PostgreSQL сам направляет строки и запросы в
нужные партиции.

**2. Чем partitioning отличается от индекса?**
Индекс — дополнительная структура, которая помогает найти нужные *строки*
внутри таблицы, не меняя её физического устройства. Партиционирование меняет
само хранение, разбивая таблицу на части, и позволяет целиком пропускать
ненужные *куски*. Индекс работает по любой проиндексированной колонке;
партиционирование — только по ключу партиционирования. Плюс у
партиционирования есть эксплуатационные возможности, которых у индекса нет
в принципе: мгновенное удаление старых данных через `DROP`/`DETACH` и
обслуживание таблицы по частям.

**3. Какие стратегии partitioning поддерживает PostgreSQL?**
`RANGE` (диапазоны значений), `LIST` (перечисление значений) и `HASH` (остаток
от деления хеша). Партиции можно вкладывать друг в друга, получая
многоуровневое партиционирование — например, RANGE по месяцу, а внутри HASH по
`user_id`.

**4. Когда использовать RANGE?**
Для непрерывных упорядоченных величин — дат, сумм, числовых диапазонов — когда
запросы фильтруют по интервалу. Главный сценарий: данные с временным жизненным
циклом, где старые периоды нужно удалять или архивировать целиком.

**5. Когда использовать LIST?**
Когда ключ принимает небольшое, стабильное и заранее известное множество
значений: тип клиента, страна, статус, регион. Запрос на равенство попадает
ровно в одну партицию.

**6. Когда использовать HASH?**
Когда нужно просто равномерно разложить данные, а естественных диапазонов или
категорий нет, и при этом основные запросы ищут по равенству ключа. В части 6
хеш дал распределение 24.94 / 25.04 / 25.01 / 25.02 процента.

**7. Как выбрать partition key?**
По колонке, которая участвует в условиях большинства тяжёлых запросов — иначе
pruning не сработает (часть 9). Дополнительно ключ должен давать партиции
сопоставимого и разумного размера и по возможности соответствовать жизненному
циклу данных. В части 12 `created_at` удовлетворяет всем трём условиям сразу.

**8. Что такое partition pruning?**
Исключение партиций, которые заведомо не содержат подходящих строк, на
основании условия по ключу партиционирования. Отсечение происходит при
планировании (а для параметров запроса — и при выполнении), поэтому
исключённые партиции не читаются вовсе и обычно даже не появляются в плане.

**9. Почему pruning может не сработать?**
Если условие поставлено не на ключ партиционирования (часть 9: фильтр по
`event_type` при разделении по `created_at`); если условие несовместимо со
стратегией — например, диапазон при HASH-партиционировании; если значение
ключа скрыто за функцией или несовпадающим типом; если запрос вообще не
содержит условия по ключу, как `GET /rentals/{id}` в части 12.

**10. Можно ли использовать индексы вместе с partitioning?**
Да, и это основной рабочий режим. `CREATE INDEX` на родительской таблице
создаёт реальный индекс в каждой партиции плюс шаблон на родителе, и все
будущие партиции получают индексы автоматически. В части 8 комбинация
pruning + индекс дала 24 буфера против 9 465 у одного pruning и 74 у одного
индекса.

**11. Что произойдёт, если подходящей партиции нет?**
Вставка завершится ошибкой `no partition of relation ... found for row`, то
есть приложение перестанет писать данные. Смягчить это можно DEFAULT-партицией
(для LIST и RANGE), но правильное решение — заранее создавать партиции
автоматически и следить за горизонтом.

**12. Зачем создавать будущие партиции заранее?**
Потому что партиция нужна в тот момент, когда приходит первая строка нового
периода, — то есть в полночь, без запаса времени на реакцию. Запас в несколько
дней или месяцев даёт возможность заметить и починить сбой автоматики раньше,
чем он превратится в отказ вставки. Это и есть смысл «горизонта» в job и
health check.

**13. Почему создание партиций должно быть автоматизировано?**
Потому что это регулярная операция без права на пропуск: один забытый день —
и запись останавливается. Человек забывает, уходит в отпуск и болеет, а job
выполняется каждую ночь и логирует результат. Вручную поддерживать сотни
партиций в год физически невозможно.

**14. Чем логирование ошибки отличается от alerting?**
Логи пассивны: запись появляется в файле, и её нужно пойти и прочитать. Alert
активен: он сам приходит к дежурному в канал, которым тот пользуется. Ошибка
в логе в 01:00 будет замечена утром — то есть после того, как приложение
начнёт падать на INSERT; alert приходит сразу. Логировать нужно всё, а
алертить — только то, что требует немедленных действий.

**15. Что такое recovery alert?**
Уведомление о том, что проблема закрыта и система вернулась в нормальное
состояние. Без него дежурный не знает, чинилась ли проблема вообще, и
вынужден проверять руками. В части 11 recovery-сообщение
(`🟢 Partition check OK`) отправляется при переходе `CRITICAL → OK`.

**16. Почему нельзя бесконечно отправлять одинаковый alert?**
Из-за этого канал превращается в шум, в котором теряются новые, действительно
важные сообщения, — дежурные перестают реагировать на уведомления вообще.
Поэтому проверка отправляет сообщение только при смене состояния: в прогоне
части 11 на девять запусков пришлось четыре уведомления, по числу реальных
переходов между OK и CRITICAL.

**17. Всегда ли partitioning ускоряет запросы?**
Нет. Оно ускоряет только те запросы, которые фильтруют по ключу
партиционирования. Остальные могут даже замедлиться: планировщик обязан
рассмотреть все партиции, план растёт, к каждой партиции идёт отдельное
обращение. В части 12 `GET /rentals/{id}` работает через `Append` по всем
четырём партициям вместо одного `Index Scan`. На таблице, которая целиком
помещается в память, партиционирование обычно не нужно вовсе.

**18. Какие проблемы возникают при неправильном выборе размера партиций?**
*Слишком мелкие партиции*: их становятся тысячи, раздувается системный каталог,
растёт время планирования (планировщик рассматривает каждую), приходится
держать огромное число индексов и файлов, а запрос за длинный период
превращается в `Append` из сотен узлов. *Слишком крупные*: pruning отсекает
мало, каждая партиция снова становится неповоротливой таблицей, а удаление
старых данных теряет гранулярность — нельзя удалить месяц, если партиция
годовая. Ориентир — партиция, сопоставимая по размеру с оперативной памятью
под кэш и соответствующая типичному диапазону запросов; в части 12 это месяц
(около 500 000 строк и 45 MB).
