# Лабораторная работа №1. Индексы и планы выполнения в PostgreSQL

Схема `krasova_lab1`, таблица `orders`, 1 000 000 строк.
Все планы и замеры в отчёте получены на живой базе; полный протокол —
запрос за запросом вместе с ответами `psql` — лежит в [`result.md`](result.md),
сырой вывод скрипта — в `results/raw_output.txt`.

Разбор по заданиям идёт ниже в четырёх блоках; краткие ответы на контрольные
вопросы собраны отдельно в разделе
[«Ответы на контрольные вопросы»](#ответы-на-контрольные-вопросы).

## Как это запускалось

| Параметр | Значение |
|---|---|
| СУБД | PostgreSQL 18.0 (Debian), контейнер `database_postgres` |
| Подключение | `postgres@localhost:5432/postgres`, параметры в `.env` проекта |
| Схема / таблица | `krasova_lab1.orders` |
| Объём | 1 000 000 строк: 77 MB heap + 21 MB первичный ключ = 98 MB |
| Пользователи | 100 000, ровно по 10 заказов на каждого |
| Статусы | 4 значения, ровно по 250 000 строк (25%) |
| Диапазон дат | 2024-09-10 … 2026-09-10 (731 день) |

Воспроизведение:

```bash
docker compose --env-file ./.env up -d          # поднять базу
psql < sql/01_schema.sql                   # схема и таблица
psql < sql/02_generate.sql                 # 1 000 000 строк + ANALYZE
./run_lab.sh                               # задания 3-15, перезапишет results/
```

`run_lab.sh` идемпотентен: перед стартом он сбрасывает все индексы, кроме
первичного ключа, поэтому повторный запуск даёт ту же последовательность
состояний. Он же перезаписывает `results/raw_output.txt` и пересобирает
`result.md`.

Все числа в этом отчёте относятся к прогону, записанному в
`results/raw_output.txt`, и каждое из них можно найти там же. Повторный запуск
даст те же планы, типы узлов и количество буферов, но другие миллисекунды —
почему на них не стоит опираться, объяснено ниже.

## Методика: почему в отчёте важнее буферы, а не миллисекунды

Три решения, без которых цифры ниже нельзя было бы сравнивать.

**Прогрев.** Каждый замеряемый запрос выполняется дважды, в отчёт идёт второй
прогон. Иначе первый запрос платит за чтение с диска, а второй нет, и разница
«до/после» отражала бы состояние кэша, а не работу индекса. Во всех планах
поэтому `shared hit=...` без `read=...`.

**Буферы как основная метрика.** Запросы, возвращающие 10 строк, выполняются за
0.07–0.3 мс. На этом масштабе разброс между повторами того же самого запроса
сопоставим с разницей между вариантами плана, и по времени ничего доказать
нельзя. `Buffers: shared hit` — детерминированная величина: она показывает,
сколько страниц исполнитель реально прочитал. Ниже время приводится, но вывод
делается по числу буферов и по типу узла плана.

**Контролируемый набор индексов.** В заданиях 12–14 недостаточно просто создать
новый индекс: если старый одиночный индекс остаётся в схеме и стоит столько же,
планировщик продолжает использовать его, и эксперимент не состоится (это видно
в задании 12, шаг «составной создан, одиночный на месте»). Поэтому для чистого
сравнения старый индекс явно удаляется, и в отчёте это оговорено.

# Блок A. Таблица без индексов (задания 1–5)

## Задание 1. Создание таблицы

Создана `orders` с колонками `id`, `user_id`, `product_id`, `status`, `amount`,
`created_at`, `updated_at`. Объявление `id BIGSERIAL PRIMARY KEY` дало
единственный на этот момент индекс — уникальный B-tree `orders_pkey`.
Больше индексов нет, и именно это делает задания 3–5 осмысленными.

## Задание 2. Генерация данных

Вставлен 1 000 000 строк одним `INSERT ... SELECT` из `generate_series`, затем
`ANALYZE orders`.

Распределения заданы детерминированно, а не случайно:

- `user_id = ((i - 1) / 10) + 1` — ровно 10 заказов у каждого из 100 000
  пользователей, то есть один пользователь это 0.001% таблицы;
- `status` берётся из массива по `i % 4` — ровно по 25% на статус;
- `created_at` — случайная точка внутри двух лет, `amount` — случайная сумма
  от 10 до 10 000.

Случайная часть зафиксирована через `setseed(0.42)`. `ANALYZE` обязателен:
без свежей статистики планировщик оценивал бы селективность по умолчанию и
дальнейшие сравнения планов потеряли бы смысл.

Первая версия генератора содержала ошибку, которую стоит назвать: выражение с
`random()` было вынесено в `LATERAL`-подзапрос, не ссылающийся на `i`, и
PostgreSQL вычислил его один раз — все 1 000 000 строк получили одну и ту же
дату. Проверка `min(created_at)`/`max(created_at)` это поймала; в рабочей версии
выражение вычисляется для каждой строки.

## Задание 3. План до создания индекса

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
```

```text
Gather  (cost=1000.00..16013.33 rows=10 width=45)
  Workers Planned: 2
  ->  Parallel Seq Scan on orders  (cost=0.00..15012.33 rows=4 width=45)
        Filter: (user_id = 123)
```

Индекса по `user_id` нет, поэтому единственный доступный способ — прочитать всю
таблицу и проверить условие у каждой строки. Таблица достаточно велика, чтобы
планировщик подключил параллельность: два рабочих процесса плюс ведущий делят
9804 страницы между собой, `Gather` собирает результат.

Оценка `rows=10` точна, потому что `ANALYZE` уже собрал статистику: 1 000 000
строк на 100 000 различных значений `user_id` дают ровно 10.

## Задание 4. `EXPLAIN` против `EXPLAIN ANALYZE`

```text
Gather  (actual time=0.372..30.515 rows=10.00 loops=1)
  Workers Launched: 2
  Buffers: shared hit=9804
  ->  Parallel Seq Scan on orders  (actual time=... rows=3.33 loops=3)
        Rows Removed by Filter: 333330
Planning Time: 0.329 ms
Execution Time: 30.587 ms
```

Чтобы вернуть 10 строк, система прочитала 9804 страницы — всю таблицу — и
отбросила фильтром по 333 330 строк в каждом из трёх процессов.

Разница между командами:

| | `EXPLAIN` | `EXPLAIN ANALYZE` |
|---|---|---|
| Выполняет запрос | нет | да |
| Что показывает | предполагаемый план и его стоимость | план плюс фактические строки, циклы, время |
| Побочные эффекты | отсутствуют | для `INSERT`/`UPDATE`/`DELETE` изменения будут применены |
| Стоимость вызова | мгновенно | равна стоимости самого запроса |

`rows=10` в скобках стоимости — оценка планировщика по статистике,
`actual rows=10.00` — фактический результат. Здесь они совпали; расхождение
между ними на порядок и больше как раз и есть типичный признак того, что
статистика устарела или условие сложнее, чем планировщик умеет оценить.

Отдельная деталь: `loops=3` означает, что узел отработал в трёх процессах, а
`rows=3.33` — среднее на процесс. Умножая, получаем те же 10 строк; читать эти
числа как «нашлось 3 строки» неверно.

## Задание 5. Sequential Scan

| Запрос | План | Строк | Буферы | Execution Time |
|---|---|---:|---:|---:|
| `SELECT * FROM orders` | Seq Scan | 1 000 000 | 9804 | 99.081 ms |
| `... WHERE amount > 0` | Seq Scan | 1 000 000 | 9804 | 169.722 ms |

Оба варианта читают одинаковое число страниц, но второй дороже: к чтению
добавляется вычисление `amount > 0` для каждой из миллиона строк, причём над
типом `numeric`, который сравнивается заметно медленнее целых чисел. Условие
при этом ничего не отсекает — минимальная сумма в данных равна 10.

Это и есть случай, когда `Seq Scan` — правильный план. Он читает страницы
подряд, что дружественно к упреждающему чтению, и не требует обращаться к
структуре индекса. Индекс по `amount` здесь только навредил бы: пришлось бы
прочитать сам индекс целиком и вдобавок сходить в heap за каждой строкой.

**Вывод блока.** `Seq Scan` плох не сам по себе, а тогда, когда после него
стоит `Rows Removed by Filter`, сопоставимое с размером таблицы, а возвращается
несколько строк. Именно это и видно в задании 4.

# Блок B. Один индекс по одной колонке (задания 6–10)

## Задание 6. B-tree по `user_id`

```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);   -- 9256 kB
```

| Метрика | До индекса | После индекса |
|---|---|---|
| Узел плана | `Gather` → `Parallel Seq Scan` | `Index Scan using idx_orders_user_id` |
| Условие | `Filter: (user_id = 123)` | `Index Cond: (user_id = 123)` |
| Прочитано буферов | 9804 | 5 |
| Отброшено фильтром | 999 990 | 0 |
| Execution Time | 30.587 ms | 0.127 ms |

Ключевая строка — не время, а переход `Filter` → `Index Cond`. `Filter` означает
«строка прочитана, потом отвергнута», `Index Cond` — «строка даже не читалась».
Поэтому вместо 9804 страниц читается 5: несколько узлов B-дерева и одна-две
страницы heap. Параллельность исчезла за ненадобностью — читать нечего.

Ускорение по времени в этом прогоне около 240 раз, но опираться стоит на
сокращение чтения почти в 2000 раз: оно не зависит от загрузки машины.

## Задание 7. Индекс при низкой селективности

```sql
CREATE INDEX idx_orders_status ON orders(status);
```

| Значение | План | Строк | Буферы (индекс + heap) | Execution Time |
|---|---|---:|---:|---:|
| `NEW` | Bitmap Index → Bitmap Heap | 250 000 | 213 + 9804 | 57.139 ms |
| `PAID` | Bitmap Index → Bitmap Heap | 250 000 | 213 + 9804 | 45.851 ms |
| `DELIVERED` | Bitmap Index → Bitmap Heap | 250 000 | 217 + 9804 | 60.297 ms |
| `CANCELLED` | Bitmap Index → Bitmap Heap | 250 000 | 216 + 9804 | 52.250 ms |

Индекс формально использован во всех четырёх случаях, но выигрыша нет:
`Heap Blocks: exact=9804` означает, что прочитаны все страницы таблицы —
ровно столько же, сколько прочёл бы `Seq Scan`, плюс ещё 213 страниц самого
индекса. Четверть строк распределена по таблице равномерно, поэтому
незатронутых страниц просто не осталось.

Планировщик выбрал этот план, потому что оценил его чуть дешевле
(≈15 700 против ≈19 800 у `Seq Scan`) — разница невелика, и при небольшом
изменении данных или настроек выбор мог бы стать другим.

## Задание 8. Исследование селективности

Все четыре статуса по построению занимают 25% таблицы, поэтому планы совпадают.
Показателен контраст с высокоселективным условием на тех же данных:

| Условие | Доля таблицы | План | Буферы | Execution Time |
|---|---:|---|---:|---:|
| `user_id = 777` | 0.001% | Index Scan | 4 | 0.128 ms |
| `status = 'NEW'` | 25% | Bitmap Heap Scan | 10 017 | 57.139 ms |

Правило, которое из этого следует: индекс окупается, когда он позволяет
**не читать** большую часть страниц. При 0.001% страниц читается 4 штуки, при
25% — все. Порог не фиксирован и зависит от того, насколько подходящие строки
сгруппированы физически (`correlation` в `pg_stats`), но по порядку величины
переход от выгодного индекса к невыгодному происходит в районе нескольких
процентов таблицы.

## Задание 9. Диапазонный запрос по дате

До создания индекса запрос за 7 дней шёл через `Parallel Seq Scan`: 9538 строк,
9804 буфера, 95.199 ms.

```sql
CREATE INDEX idx_orders_created_at ON orders(created_at);
```

| Диапазон | Строк | Доля | План | Буферы | Execution Time |
|---|---:|---:|---|---:|---:|
| 1 день | 1 354 | 0.14% | Bitmap Heap Scan | 1 272 | 5.711 ms |
| 7 дней | 9 538 | 0.95% | Bitmap Heap Scan | 6 136 | 13.507 ms |
| 1 месяц | 42 161 | 4.2% | Bitmap Heap Scan | 9 791 | 25.267 ms |
| 1 год | 500 330 | 50% | **Seq Scan** | 9 804 | 250.334 ms |

Здесь виден весь переход целиком, и интереснее всего строка «1 месяц»: индекс
ещё используется, но прочитано уже 9791 страница из 9804 — выгода исчезла
раньше, чем планировщик отказался от индекса. На интервале в год он от индекса
отказывается: половина таблицы дешевле читается подряд.

Причина — физическое расположение данных. `created_at` сгенерирован случайно, и
строки одного дня разбросаны по всей таблице: 1354 строки лежат на 1263 разных
страницах, то есть практически каждая на своей. Если бы таблица была
упорядочена по дате (как бывает при последовательной вставке), тот же индекс
оставался бы выгодным на куда более широких диапазонах.

## Задание 10. Bitmap Scan

```text
Bitmap Heap Scan on orders  (rows=250000, Heap Blocks: exact=9804)
  Recheck Cond: ((status)::text = 'NEW'::text)
  ->  Bitmap Index Scan on idx_orders_status  (rows=250000, Buffers: shared hit=213)
        Index Cond: ((status)::text = 'NEW'::text)
```

План работает в две фазы. `Bitmap Index Scan` целиком проходит нужную часть
индекса и строит битовую карту страниц, содержащих подходящие строки, — но
самих строк не читает. `Bitmap Heap Scan` затем обходит heap **в порядке
возрастания номеров страниц**, читая каждую нужную страницу ровно один раз.

Смысл именно в порядке. Обычный `Index Scan` шёл бы по heap в порядке ключа
индекса, то есть прыгал бы по таблице случайно и мог бы возвращаться к одной
странице многократно. Bitmap превращает случайный доступ в последовательный,
и это его главное преимущество на среднем количестве строк.

Строка `Recheck Cond` — не дублирование работы: если строк слишком много,
битовая карта переходит в «lossy»-режим и хранит только номера страниц без
позиций внутри них, и тогда условие приходится перепроверять. Здесь карта
поместилась в память точно (`exact`), и перепроверка фактически не понадобилась.

# Блок C. Несколько колонок (задания 11–13)

## Задание 11. Два отдельных индекса в одном запросе

В схеме есть `idx_orders_user_id` и `idx_orders_status`. Запрос:

```sql
SELECT * FROM orders WHERE user_id = 123 AND status = 'PAID';
```

```text
Index Scan using idx_orders_user_id on orders  (rows=3.00) 
  Index Cond: (user_id = 123)
  Filter: ((status)::text = 'PAID'::text)
  Rows Removed by Filter: 7
  Buffers: shared hit=5
Execution Time: 0.087 ms
```

Использован ровно один индекс из двух; второе условие проверено обычным
фильтром. `BitmapAnd` не появился, и это правильное решение: пересечение
означало бы построение битовой карты из 250 000 ссылок по статусу ради того,
чтобы отсечь 7 строк из 10 уже найденных. Дешевле прочитать 10 строк и
проверить у них поле.

Отсюда общее правило: наличие индексов на обе колонки не гарантирует, что
использованы будут оба. PostgreSQL применяет `BitmapAnd`, когда обе части
по отдельности возвращают много строк, а их пересечение — мало.

## Задание 12. Составной индекс

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
```

Первый замер после создания дал неожиданный результат — план не изменился,
по-прежнему использовался `idx_orders_user_id` с фильтром по статусу.
Причина в стоимости: `8.62` у одиночного индекса против `10.21` у составного.
Составной индекс шире, его страницы вмещают меньше записей, а выигрыш от
проверки статуса внутри индекса на десяти строках нулевой.

Чтобы увидеть работу составного индекса, одиночный был временно удалён:

| Вариант | План | Условие | Стоимость | Буферы | Время |
|---|---|---|---:|---:|---:|
| `idx_orders_user_id` + фильтр | Index Scan | `Index Cond: user_id`, `Filter: status`, 7 строк отброшено | 8.62 | 5 | 0.081 ms |
| `idx_orders_user_status` | Index Scan | `Index Cond: (user_id = 123) AND (status = 'PAID')` | 10.21 | 5 | 0.086 ms |

Составной индекс делает ровно то, что от него ожидается: оба условия ушли в
`Index Cond`, строка `Rows Removed by Filter` исчезла. Но выигрыша по чтению
нет — те же 5 буферов, потому что отбрасывать было нечего.

Составной индекс окупился бы при другом соотношении: например, если бы у
пользователя было 10 000 заказов и лишь несколько в статусе `PAID`. Обратная
сторона — он полезен только запросам, начинающимся с `user_id`, занимает больше
места и обновляется при каждой записи.

## Задание 13. Порядок колонок

Два индекса проверены по отдельности, чтобы они не конкурировали друг с другом
и с одиночными индексами.

**Вариант A — единственный индекс `(user_id, created_at)`:**

| Запрос | План | Буферы | Время |
|---|---|---:|---:|
| `user_id = 123` | Index Scan, `Index Cond: user_id` | 11 | 0.091 ms |
| `user_id = 123` + диапазон дат | Index Scan, **оба условия в `Index Cond`** | 11 | 0.064 ms |
| только диапазон дат | **Parallel Seq Scan** | 9 804 | 95.909 ms |

**Вариант B — единственный индекс `(created_at, user_id)`:**

| Запрос | План | Буферы | Время |
|---|---|---:|---:|
| `user_id = 123` | **Parallel Seq Scan** | 9 804 | 30.954 ms |
| `user_id = 123` + диапазон дат | Index Scan, `Index Cond: created_at ... AND user_id` | 1 937 | 15.188 ms |
| только диапазон дат | Bitmap Heap Scan | 1 274 | 5.427 ms |

Результат симметричен и объясняется правилом левого префикса. B-tree хранит
записи, отсортированные сначала по первой колонке, и только внутри равных
значений первой — по второй. Использовать индекс для поиска можно, лишь если
задано значение первой колонки: иначе нужные записи не образуют непрерывного
отрезка дерева.

Поэтому вариант A бесполезен для запроса только по дате, а вариант B —
для запроса только по `user_id`.

Особенно показателен второй запрос. Оба индекса формально приняли оба условия
в `Index Cond`, но вариант A прочитал 11 страниц, а вариант B — 1937.
В варианте B ведущая колонка `created_at` задаёт диапазон длиной в год, то есть
половину индекса, и внутри этого диапазона `user_id` работает уже не как
ограничитель поиска, а как проверка каждой встреченной записи. В варианте A
ведущий `user_id` сразу сужает поиск до 10 записей, среди которых дата
отсекает лишние.

Отсюда практическое правило: первой в составном индексе ставится колонка,
по которой идёт сравнение на равенство, а колонка диапазона — после неё.

# Блок D. Сортировка и пагинация (задания 14–15)

## Задание 14. `WHERE` + `ORDER BY`

```sql
SELECT * FROM orders WHERE user_id = 123 ORDER BY created_at DESC;
```

Исходное состояние — одиночный `idx_orders_user_id`:

```text
Sort  (Sort Key: created_at DESC, Sort Method: quicksort  Memory: 25kB)
  ->  Index Scan using idx_orders_user_id  (Index Cond: user_id = 123)
Execution Time: 0.129 ms
```

Индекс нашёл строки, но порядок пришлось создавать отдельным узлом `Sort`.
Одиночный индекс заменён на составной с нужным направлением:

```sql
DROP INDEX idx_orders_user_id;
CREATE INDEX idx_orders_user_created_desc ON orders(user_id, created_at DESC);
```

```text
Index Scan using idx_orders_user_created_desc  (Index Cond: user_id = 123)
Execution Time: 0.073 ms
```

| Метрика | До | После |
|---|---|---|
| Узел `Sort` | есть, quicksort, 25 kB | **отсутствует** |
| Буферы | 8 | 11 |
| Execution Time | 0.129 ms | 0.073 ms |

Узел `Sort` исчез полностью. B-tree физически хранит ключи в отсортированном
виде, поэтому обход диапазона одного пользователя уже выдаёт строки в порядке
`created_at DESC` — сортировать нечего.

Два замечания к этому результату.

Порядок колонок обязателен именно такой. Сначала `user_id` формирует
непрерывный отрезок индекса, принадлежащий одному пользователю, и уже внутри
этого отрезка даты идут по убыванию. При обратном порядке отрезок одного
пользователя не был бы непрерывным.

Буферов стало больше (11 против 8), а не меньше: составной индекс шире
одиночного, и его страницы вмещают меньше записей. Выигрыш здесь не в объёме
чтения, а в устранении сортировки — и он станет решающим, когда строк у
пользователя будут не десятки, а десятки тысяч: `Sort` требует материализовать
и упорядочить весь результат, тогда как упорядоченный `Index Scan` может отдать
первые строки сразу.

## Задание 15. Pagination Query

```sql
SELECT * FROM orders WHERE user_id = 123 ORDER BY created_at DESC LIMIT 20;
```

Отправная точка — индекс из задания 14; сортировки уже нет, `LIMIT` просто
останавливает `Index Scan`. Оптимизация:

```sql
DROP INDEX idx_orders_user_created_desc;
CREATE INDEX idx_orders_pagination
  ON orders(user_id, created_at DESC)
  INCLUDE (id, product_id, status, amount, updated_at);
VACUUM (ANALYZE) orders;
```

| Метрика | `(user_id, created_at DESC)` | + `INCLUDE` (покрывающий) |
|---|---|---|
| План | `Limit` → `Index Scan` | `Limit` → **`Index Only Scan`** |
| Обращения к heap | есть | `Heap Fetches: 0` |
| Буферы | 11 | **4** |
| Стоимость | 0.42..24.35 | 0.42..4.60 |
| Медиана из 15 прогонов | 0.087 ms | 0.081 ms |
| Размер индекса | 30 MB | 69 MB |

`INCLUDE` дописывает в листья индекса остальные колонки из `SELECT *`, не
делая их частью ключа. В результате индекс содержит всё необходимое для ответа,
и heap не нужен вовсе — `Heap Fetches: 0`. Это работает только потому, что
`VACUUM` обновил visibility map: без него PostgreSQL был бы вынужден ходить в
heap за проверкой видимости каждой строки, и `Index Only Scan` потерял бы смысл.

**По времени выигрыша нет.** 15 повторов каждого варианта дают медианы
0.081 мс против 0.087 мс при разбросе от 0.059 до 0.275 мс — разница между
вариантами меньше разброса внутри каждого из них, и в предыдущем прогоне
знак этой разницы был обратным. Причина в масштабе задачи: у пользователя
всего 10 заказов, и 0.08 мс — это почти целиком накладные расходы исполнителя,
а не чтение данных. Сэкономленные 7 страниц из кэша ничего не стоят.

Честный вывод: покрывающий индекс сократил объём чтения в 2.75 раза (11 → 4
буфера) и убрал обращения к heap, но на этих данных это не конвертируется в
скорость. Он окупился бы при большой странице выдачи и холодном кэше, когда
каждое обращение к heap — реальный дисковый ввод-вывод. Цена при этом вполне
осязаема: 69 MB против 30 MB, то есть индекс вырос более чем вдвое и почти
сравнялся по размеру с самой таблицей (77 MB), а каждый `INSERT`/`UPDATE`
теперь обновляет в нём ещё пять дополнительных колонок.

Для настоящего сервиса разумнее не `SELECT *`, а перечисление нужных API полей,
и тогда список `INCLUDE` сокращается до одной-двух колонок либо не нужен вовсе.

## Задание 4

**В чём разница между `EXPLAIN` и `EXPLAIN ANALYZE`?**
`EXPLAIN` только строит план и показывает оценки, запрос при этом не
выполняется. `EXPLAIN ANALYZE` реально выполняет запрос и добавляет фактические
значения: `actual time`, `actual rows`, `loops`, `Rows Removed by Filter`.
Отсюда два следствия: вызов стоит столько же, сколько сам запрос, и для
`INSERT`/`UPDATE`/`DELETE` изменения будут применены (чтобы этого избежать,
команду оборачивают в транзакцию с `ROLLBACK`).

**Чем `rows` отличается от `actual rows`?**
`rows` в скобках стоимости — предсказание планировщика по статистике,
`actual rows` — фактически полученное число строк. Здесь обе величины равны 10.
Расхождение на порядок и более — типичный признак устаревшей статистики или
условия, селективность которого планировщик оценить не умеет.

**Что означают `loops=3` и `rows=3.33` у узла `Parallel Seq Scan`?**
Узел отработал в трёх процессах, а `rows` — среднее на один процесс, а не
итог. Фактическое число строк равно `rows × loops`, то есть 10. По той же
причине `Rows Removed by Filter: 333330` — это на процесс, суммарно отброшено
999 990 строк.

**Почему запрос медленный?**
Чтобы вернуть 10 строк, прочитано 9804 буфера — вся таблица.

## Задание 5

**Какой план выбран для обоих запросов?**
`Seq Scan` в обоих случаях: без `WHERE` нужна вся таблица, а условие
`amount > 0` не отсекает ничего: по формуле генератора
`round(random() * 9990 + 10, 2)` сумма не может быть меньше 10.

**Почему запрос с `WHERE` медленнее запроса без `WHERE` (169.722 мс против
99.081 мс), хотя возвращает столько же строк?**
Читается одинаковое число страниц — 9804, но во втором случае к чтению
добавляется вычисление предиката для каждой из 1 000 000 строк, причём над
типом `numeric`, который сравнивается заметно медленнее целочисленных типов.

**Когда `Sequential Scan` эффективен?**
Когда нужна вся таблица или значительная её часть. Он читает страницы подряд,
что дружественно к упреждающему чтению, и не требует ни чтения индекса, ни
случайных обращений к heap. Индекс по `amount` здесь только навредил бы.

**Значит, `Seq Scan` — это всегда плохо?**
Нет. Плох он только тогда, когда после него стоит `Rows Removed by Filter`,
сопоставимое с размером таблицы, а возвращается несколько строк — как в
задании 4.

## Задание 10

**Как работает `Bitmap Scan`?**
В две фазы. `Bitmap Index Scan` проходит нужную часть индекса и строит битовую
карту страниц, содержащих подходящие строки, самих строк при этом не читая.
`Bitmap Heap Scan` затем обходит heap в порядке возрастания номеров страниц,
читая каждую нужную страницу ровно один раз.

**Чем он лучше обычного `Index Scan`?**
Порядком доступа. `Index Scan` идёт по heap в порядке ключа индекса, то есть
прыгает по таблице случайно и может возвращаться к одной странице многократно.
Bitmap превращает случайный доступ в последовательный.

**Когда он выгоден?**
На среднем количестве строк: когда их слишком много для `Index Scan` с его
случайными чтениями, но ещё слишком мало, чтобы читать всю таблицу подряд.

**Зачем нужна строка `Recheck Cond`?**
Если подходящих строк слишком много, битовая карта не помещается в
`work_mem` и переходит в режим «lossy»: хранит только номера страниц, без
позиций строк внутри них. Тогда условие приходится перепроверять для каждой
строки на такой странице. Здесь карта поместилась точно (`Heap Blocks: exact`),
и перепроверка фактически не потребовалась.

## Задание 13

**Чем различаются индексы `(user_id, created_at)` и `(created_at, user_id)`?**
Физическим порядком записей. B-tree сортирует сначала по первой колонке и
только внутри равных её значений — по второй.

**Что такое правило левого префикса?**
Индекс применим для поиска, только если задано значение первой колонки: иначе
подходящие записи не образуют непрерывного отрезка дерева. Поэтому
`(user_id, created_at)` бесполезен для запроса только по дате (`Parallel Seq
Scan`, 9804 буфера), а `(created_at, user_id)` — для запроса только по
`user_id` (`Parallel Seq Scan`, 9804 буфера).

**Какой индекс для какого запроса подходит?**
`(user_id, created_at)` — для заказов конкретного пользователя, в том числе за
период. `(created_at, user_id)` — для выборки за период по всем пользователям.

**Оба индекса приняли оба условия в `Index Cond`. Почему тогда один прочитал
11 буферов, а другой 1937?**
Это самый показательный результат задания. В варианте `(created_at, user_id)`
ведущая колонка задаёт диапазон длиной в год, то есть половину индекса, и
внутри него `user_id` работает уже не как ограничитель поиска, а как проверка
каждой встреченной записи. В варианте `(user_id, created_at)` ведущий `user_id`
сразу сужает поиск до 10 записей, среди которых дата отсекает лишние.

**Какое практическое правило отсюда следует?**
Первой в составном индексе ставится колонка, по которой идёт сравнение на
равенство, а колонка диапазона — после неё.

## Задание 14

**Исчез ли узел `Sort` после создания индекса?**
Да. До оптимизации план был `Sort` (quicksort, 25 kB) над `Index Scan`, после —
чистый `Index Scan using idx_orders_user_created_desc` без сортировки.

**Почему индекс позволяет не сортировать?**
B-tree физически хранит ключи в отсортированном виде. Обход отрезка индекса,
принадлежащего одному пользователю, сразу выдаёт строки в порядке
`created_at DESC` — сортировать нечего.

**Почему `user_id` должен быть первым?**
Сначала `user_id` формирует непрерывный отрезок индекса, принадлежащий одному
пользователю, и уже внутри этого отрезка даты идут по убыванию. При обратном
порядке колонок строки одного пользователя не лежали бы подряд, и упорядоченный
проход по ним был бы невозможен.

**Почему буферов стало больше (8 → 11), если план улучшился?**
Составной индекс шире одиночного, его страницы вмещают меньше записей.
Выигрыш здесь не в объёме чтения, а в устранении сортировки. Он станет
решающим, когда строк у пользователя будут не десятки, а десятки тысяч: `Sort`
обязан материализовать и упорядочить весь результат, тогда как упорядоченный
`Index Scan` отдаёт первые строки сразу.

## Задание 15

**Какой индекс выбран для оптимизации пагинации?**

```sql
CREATE INDEX idx_orders_pagination
  ON orders(user_id, created_at DESC)
  INCLUDE (id, product_id, status, amount, updated_at);
```

**Почему именно такой?**
`user_id` первым даёт точный поиск нужного пользователя; `created_at DESC`
сразу обеспечивает порядок выдачи, поэтому `Sort` не нужен, а `LIMIT 20` может
остановить сканирование на первых строках; `INCLUDE` дописывает в листья
индекса остальные колонки из `SELECT *`, не делая их частью ключа, — благодаря
этому индекс содержит всё необходимое для ответа.

**Что изменилось в плане?**
`Index Scan` заменился на `Index Only Scan` с `Heap Fetches: 0`: к таблице
запрос не обращается вовсе. Буферы сократились с 11 до 4, оценка стоимости —
с 24.35 до 4.60.

**Зачем понадобился `VACUUM (ANALYZE)`?**
`Index Only Scan` обязан убедиться в видимости каждой строки. Если visibility
map не обновлена, PostgreSQL вынужден ходить за этим в heap, и `Heap Fetches`
перестал бы быть нулевым — то есть основной смысл покрывающего индекса
потерялся бы.

**Насколько ускорился запрос?**
По времени — никак. 15 повторов каждого варианта дают медианы 0.081 мс против
0.087 мс при разбросе от 0.059 до 0.275 мс: разница между вариантами меньше
разброса внутри каждого из них, а в предыдущем прогоне её знак был обратным.
У пользователя всего 10 заказов, и 0.08 мс — это почти целиком накладные
расходы исполнителя, а не чтение данных. Реальный результат оптимизации —
сокращение чтения в 2.75 раза (11 → 4 буфера) и отсутствие обращений к heap;
в скорость это превратится при большой странице выдачи и холодном кэше, когда
каждое обращение к heap означает дисковый ввод-вывод.

**Какова цена такого индекса?**
69 MB против 30 MB у обычного `(user_id, created_at DESC)` — рост более чем
вдвое, почти до размера самой таблицы (77 MB). Каждый `INSERT`/`UPDATE` теперь
обновляет в индексе ещё пять дополнительных колонок. В настоящем сервисе
разумнее не `SELECT *`, а перечисление нужных API полей: тогда список
`INCLUDE` сокращается до одной-двух колонок либо не нужен вовсе.

# Итоги

**Что индекс делает на самом деле.** Он не «ускоряет запрос», а сокращает
объём чтения. Все замеры выше — про одно: `Filter: ...` с большим
`Rows Removed by Filter` означает прочитанные и выброшенные страницы, а
`Index Cond: ...` означает, что страницы не читались. В задании 6 это 9804
буфера против 5.

**Когда индекс не помогает.**

- Возвращается большая доля таблицы — задание 7 (25% строк, прочитаны все
  9804 страницы) и задание 9 (интервал в год, планировщик сам отказался от
  индекса).
- Нужные строки физически разбросаны — задание 9: 1354 строки одного дня лежат
  на 1263 разных страницах.
- Запрос не начинается с ведущей колонки составного индекса — задание 13,
  оба варианта.
- Уже существующий индекс дешевле — задания 12 и 14, где новый индекс
  игнорировался, пока старый оставался в схеме.

**Порядок колонок решает.** Задание 13 даёт готовое правило: равенство —
первым, диапазон — вторым. Один и тот же запрос по двум условиям обошёлся
в 11 буферов при порядке `(user_id, created_at)` и в 1937 при обратном.

**Цена индексов.** Итоговый покрывающий индекс занимает 69 MB при таблице
в 77 MB. Индексы замедляют запись и занимают место, поэтому набор индексов
определяется реальными запросами приложения, а не списком колонок таблицы.

**Как проверять.** Порядок один и тот же: `EXPLAIN (ANALYZE, BUFFERS)` до
изменения, изменение, тот же замер после, сравнение. Смотреть при этом нужно
на тип узла, `Index Cond` против `Filter`, `Rows Removed by Filter` и буферы —
время само по себе на малых объёмах ничего не доказывает, что прямо видно в
задании 15.
